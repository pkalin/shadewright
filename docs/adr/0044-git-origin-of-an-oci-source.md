# ADR-0044: The Git origin of an OCI source is declared, and the artifact is only a cross-check

- Status: Proposed
- Date: 2026-11-19

## Context

Issue [#935](https://github.com/pkalin/shadewright/issues/935). The source mapping of [ADR-0012](0012-object-to-source-mapping.md) follows a Flux Kustomization to its `GitRepository` and refuses every other source: the request ends `NeedsIntervention` with `UnsupportedSource`. Many clusters deliver through OCI artifacts instead. CI builds an artifact from a Git repository (`flux push artifact`) and pushes it to a registry, and Flux pulls it through an `OCIRepository`. The desired state still lives in Git, but an `OCIRepository` says where the artifact is, not which repository, branch and path it was built from. Those clusters get diagnoses and issues, never a pull request.

Today's code, so the change is read against it:

- A Kustomization whose `spec.sourceRef.kind` is not `GitRepository` stops the mapping with `UnsupportedSource` (`internal/gitops/sourcemap/fluxrules/flux.go:93-95`; the reason is defined at `fluxrules/result.go:87-88`).
- Flux objects are read as unstructured objects, and `go.mod` has no Flux module (`flux.go:43-44`). Only the fields the rules name are used.
- A `GitRepository` passes only when it sets none of `suspend`, `ignore`, `recurseSubmodules` or `sparseCheckout` (`flux.go:63`), and tracks one branch (`flux.go:258`); the Kustomization must have applied the revision the source last fetched (`flux.go:307`, `internal/fluxstatus/fluxstatus.go:227`).
- The source URL must equal exactly one repository of the settings, that repository must be the policy's `gitOps.repositoryRef`, and the branch must equal its `targetBranch` (`sourcemap.go:331-355`). The URL is never put in a message (`sourcemap.go:330`).
- The base commit of the pull request is the head of that branch, read from the Git provider at mapping time (`sourcemap.go:233`, `sourcemap.go:308`). The freshness check runs the mapping again with the settings' repositories and compares repository, branch, path and build directory, not the base commit (`internal/policy/freshness/freshness.go:651-666`, `freshness.go:683`).
- The executor's cluster-wide role has `get` on `kustomizations` and `gitrepositories` and nothing on `ocirepositories` (`config/rbac/executor/role.yaml:23` and `:36`, from the markers at `internal/controller/cache.go:57-58`; the chart's `dist/chart/templates/rbac/executor-role.clusterrole.yaml:24` and `:37`).
- After the merge, the delivery check reads a commit out of the Kustomization's `lastAppliedRevision` only when its source is a `GitRepository` (`internal/providers/delivery/flux/flux.go:154`, `flux.go:236-237`). The unit is `Applied` when that commit equals the merge commit, or descends from it by the plan repository's ancestry answer (`internal/providers/delivery.go:146`, `delivery.go:159-185`). A unit that never shows such a commit ends the check `DeliveryNotObserved` after the delivery window, one hour (`internal/controller/rollout.go:70`, `rollout.go:510`).
- A read of a Flux object that the API server refuses (403 or 401) comes back from the delivery adapter as `providers.ErrForbidden` (`internal/providers/delivery/flux/flux.go:281-282`). `lastingCause` does not list it (`internal/controller/phases.go:383-397`), so the controller treats it as any failed read: retry with backoff, and nothing ends the request until the window or the grace period passes.
- Once a unit is `Applied`, the verification reads the live field and ends the request `Inconclusive` with `ValueChanged` at once when it differs from the desired value (`phases.go:555-567`). The text says "a later commit or change overwrote it, so this change never ran as merged" (`phases.go:689`).
- The delivery adapter's `Verifier.Verify` (`flux.go:125-132`) is the executor's path; `StatusReader.Status` (`flux.go:149`) is the read that does not compare an OCI source and stays as it is.

The last point matters most. For an OCI source the Kustomization applies `<tag>@sha256:<digest>` of the artifact (upstream: the revision of an `OCIRepository` artifact is the tag and the digest of the OCI artifact, [source-controller spec, "Artifact"](https://github.com/fluxcd/source-controller/blob/main/docs/spec/v1/ocirepositories.md)). It names no Git commit. The cluster applies an artifact CI built after the merge, never the merge commit itself.

This ADR widens a read (the executor reads `OCIRepository` objects) and the places a pull request can come from (a workload delivered through a declared artifact). [ADR-0021](0021-amending-accepted-adrs.md) says an amendment never widens on its own authority, so it is decided here and ADR-0012 gets only a pointer after acceptance. [ADR-0043](0043-the-executor-follows-its-own-pull-request-to-any-base.md) is the model: say what is widened, say what never happens, state the limits.

### What the upstream Flux API gives

Read from the current upstream documentation and source on 2026-11-19, not from memory (the repository vendors no Flux types, so there is no pinned version to read; the code reads `source.toolkit.fluxcd.io/v1`, `internal/fluxstatus/fluxstatus.go`):

- `OCIRepository` status carries `status.artifact` (type `meta.Artifact` of `fluxcd/pkg/apis/meta`): `revision`, `digest`, `url`, `size`, `lastUpdateTime` and `metadata`, a map of strings "such as OCI annotations".
- When the artifact was created with `flux push artifact`, `metadata` holds `org.opencontainers.image.created`, `org.opencontainers.image.source` ("the URL of the Git repository containing the source files") and `org.opencontainers.image.revision` ("the Git branch and commit SHA1 of the source files"). The Flux CLI requires `--source` and `--revision` and documents `--revision="$(git branch --show-current)@sha1:$(git rev-parse HEAD)"` (`cmd/flux/push_artifact.go` in fluxcd/flux2). The CLI strips credentials from the source it records. An artifact pushed by another tool, or with another `--revision`, can carry any value or none: the status example in the spec even shows `6.1.8/b3b00fe3...` as the revision annotation.
- The status of an `OCIRepository` has no field that says which Git repository, branch or path the content came from, other than those annotations. Without them there is nothing to read in the cluster. Registry access would be needed for anything else, and the executor has none.
- `spec.ref` (`tag`, `semver`, `digest`), `spec.ignore`, `spec.layerSelector`, `spec.suspend`, `spec.verify` and `spec.secretRef` or `spec.serviceAccountName` exist in the spec. For an OCIRepository, source-controller leaves out what the default exclusion rules and any `.sourceignore` file match when it archives the pulled contents, and `spec.ignore` overrides the defaults ([source-controller spec, "Ignore"](https://github.com/fluxcd/source-controller/blob/main/docs/spec/v1/ocirepositories.md), read 2026-11-19). That is a second filter: CI builds the artifact with `flux push artifact`, which has its own `--ignore-paths` (default `excludeOCI`) and `--add-ignore-paths` and passes them to `oci.WithPushIgnorePaths` (`cmd/flux/push_artifact.go` in fluxcd/flux2, read 2026-11-19). A file either step leaves out is not in the artifact, whatever Git holds.
- `spec.verify` is `OCIRepositoryVerification` (`api/v1/ociverification_types.go:23-48` in fluxcd/source-controller at `main`, read 2026-11-19): `provider` (`cosign` or `notation`, default `cosign`), `secretRef` (cosign public keys, or the notation trust policy), `matchOIDCIdentity` (a list of `OIDCIdentityMatch`, cosign keyless only) and `trustedRootSecretRef` (a Sigstore `trusted_root.json`, for a self-hosted Sigstore). `OIDCIdentityMatch` (`ociverification_types.go:70-82`) has `issuer` and `subject`, "the regex pattern ... must be a valid Go regular expression". The spec says the matchers are evaluated in an OR fashion and gives the Go (RE2) syntax; its examples anchor the patterns by hand (`^https://token.actions.githubusercontent.com$`), so the controller does not anchor them for the user (`docs/spec/v1/ocirepositories.md`, "Keyless verification"). Keyless is the path taken when `provider` is `cosign` and `secretRef` is empty (`internal/controller/ocirepository_controller.go` around line 902); the controller passes `issuer` and `subject` as `IssuerRegExp` and `SubjectRegExp` to the cosign verifier (the same file, around lines 906-909).
- Flux reports verification in the status conditions: type `SourceVerified` (`SourceVerifiedCondition`, `api/v1/condition_types.go:35-40`). It is `True` with reason `Succeeded` when the signature verified; on a failure it is `False` with reason `VerificationError` (`condition_types.go:74-76`, set at `ocirepository_controller.go` around lines 545-553 with the message "failed to verify the signature using provider ..."), and the controller retries with backoff. The condition exists only while `spec.verify` is set (`condition_types.go:35-39`; the controller deletes it when `spec.verify` is empty, `ocirepository_controller.go` around line 536). It carries the `observedGeneration` of the spec it judged, which the controller compares with the generation to decide whether to verify again (around line 539).
- The signature covers the artifact's digest, and the digest covers the manifest, so the annotations of a verified artifact are what the signer pushed. The fields read above hold no signer identity: the status has the verdict (`SourceVerified`) and a fingerprint of the policy (`sourceVerificationFingerprint`), so the executor judges the rule the cluster's operator wrote in `spec.verify`, never the identity that matched.
- `go.mod` has no Flux module, so there is no version of these types in the repository to read; the lines above are upstream `main` on the date given, not a pinned release. The executor reads unstructured objects and the names of these fields and conditions are a contract of the `v1` API, which the build pins with the test fixtures it copies from a real object.

## Decision

[![The executor reads three things: the Kustomization and its OCIRepository status in the cluster, the declaration in RemediationSettings, and the Git repository through the Git App. The declaration says which repository and path the artifact is built from; the artifact's source and revision annotations are only compared with it. No declaration, a mismatch, an artifact without annotations and an artifact Flux did not verify and an OCIRepository the executor may not read each end NeedsIntervention with their own reason and no Git write. Flux verifies the signature of the artifact; the executor reads only the verification setting, its verdict and, for a keyless signature, whether the signer identity names the declared repository. The executor never reads the registry, the artifact's content or any secret.](../assets/diagrams/oci-source-origin.svg)](../assets/diagrams/oci-source-origin.svg "Open full size")

This is option 3 of the issue, with one change: the declaration has no `branch` field. The artifact must also be signed: the mapping reads the annotations only from an artifact Flux verified (section 2, step 4).

### 1. The declaration

`RemediationSettings` gets a new list, `spec.ociSources`, next to `spec.repositories`:

```yaml
spec:
  repositories:
  - name: fleet
    url: https://github.com/example/fleet
    targetBranch: main
    provider: GitHub
    github: { ... }
  ociSources:
  - name: apps                  # Name, the list key
    ociRepository:
      namespace: flux-system    # DNS label
      name: apps                # DNS subdomain
    repositoryRef: fleet        # Name of an entry in spec.repositories
    path: clusters/prod         # GitDirPath, default "."
    verification: Required      # Required (default) or NotRequired
```

- `ociRepository` is the Flux object, by namespace and name. A pair appears at most once (a CEL rule, as the URL rule of `repositories`).
- `repositoryRef` must name an entry of `spec.repositories` (a CEL rule on the spec). The mapping checks it again and never relies on admission alone.
- `path` is the directory of the repository that the artifact's root corresponds to, `.` when CI packs the repository root (`flux push artifact --path=./clusters/prod` is `path: clusters/prod`). The build directory of a request is the Kustomization's `spec.path` put under this path, in two steps (section 2, step 7): the `spec.path` is checked on its own first, so it cannot climb out of the declared path.
- The branch is not declared. It is the `targetBranch` of the entry `repositoryRef` names, as for a `GitRepository` (ADR-0012 step 2: the branch Flux tracks must equal it). A second field could only repeat that value or disagree with it, and a disagreement would be a state to validate and to explain. The issue lists the branch among the fields; this is a deliberate departure, open for the maintainer under Open points.
- `verification` is `Required` unless the entry says `NotRequired`. `Required` is the default and the only value a person gets by leaving the field out. `NotRequired` makes the mapping accept an `OCIRepository` without `spec.verify`, and skips the identity rule of section 2, step 4. Its risk is stated in the field's documentation and in known limit (a): anyone who can write to the registry can then make the annotations match the declaration, so the annotations guard against mistakes and drift only. It is a decision of whoever writes `RemediationSettings`, per origin, and nothing in the artifact or the cluster can turn it on.
- At most 16 entries, as `repositories`.
- Fields of the `RemediationSettings` status are never read for any decision, as before.

### 2. What the mapping does for a Kustomization whose `sourceRef.kind` is `OCIRepository`

In this order, each stop being `NeedsIntervention` unless said otherwise. A read that fails is returned for retry and is never one of these stops (the rule of `Resolver.get`, `sourcemap.go:315-327`); the one exception is a refused read (point 2).

1. No `ociSources` entry names that namespace and name: stop, reason `OCIOriginNotDeclared`. The message names the object and the field to declare.
2. Read the `OCIRepository` (`get`, by the Kustomization's `spec.sourceRef`, the namespace defaulting to the Kustomization's as for a `GitRepository`, `flux.go:97-99`). Not found: `SourceNotFound`. A 403 or 401 on the read (the grant of section 3 is off): `OCISourceNotReadable`, since a retry could never succeed and would run without end and without a signal. The same read, made later by the delivery check, ends the request at once with the same reason (section 5).
3. The object must not set `spec.suspend`, `spec.ignore` or `spec.layerSelector`: reason `SourceOptions`, as for the `GitRepository` options at `flux.go:63`. Each can make the artifact differ from the files in Git. A `.sourceignore` file stops the mapping in the Git tree as today. `spec.ref` is not constrained: the revision comes from the status. `spec.verify` is judged in step 4.
4. It must be Ready for its current generation (`SourceNotReady`), signed by a signer the cluster's operator chose, and applied:
   - **Verified.** `spec.verify` must be set, and the condition `SourceVerified` must be `True` with an `observedGeneration` equal to the object's generation. Otherwise, with `spec.verify` unset or `SourceVerified` missing, `False` (Flux reason `VerificationError`) or stale: `OCISourceUnverified`. The executor reads the spec and the status only; it makes no registry call and holds no key or credential, so the verification is Flux's, and what the executor adds is the identity rule below. A failed verification is a stop, not a wait: Flux retries it with backoff, and a person re-triggers the request when it verifies. The check can be turned off per origin (`verification: NotRequired` in the declaration, section 1): this step and the identity rule are then skipped, and the cross-check of step 6 is the only guard (known limit (a)).
   - **The identity names the declared repository** (a keyless cosign verification only: `provider` `cosign`, no `secretRef`). `issuer` and `subject` are regular expressions the cluster's operator wrote, and the executor does not evaluate them against anything. It reads each pattern as text, parses it with Go's `regexp/syntax` and accepts only a pattern that is an anchored literal: `^`, one literal and `$`, nothing else, no flags (so `(?i)` is refused) and no escape that stands for anything but itself. A pattern with an unescaped `.` parses as "any character" and is refused: the operator must write `\.`. The rule is applied to every entry of `matchOIDCIdentity`, since Flux accepts the artifact when any one entry matches. For a repository of provider `GitHub` the literals must be:
     - `issuer`: exactly `https://token.actions.githubusercontent.com`;
     - `subject`: `https://github.com/<owner>/<repo>/.github/workflows/<file>@refs/heads/<branch>`, where owner and repo are those of the declared repository (ASCII case folded as in step 6, the character after the repository name being `/`, so `repo-evil` never passes) and the branch is its `targetBranch`; the file is any non-empty name without `/`. Nothing else is allowed in the literal, so there is no wildcard for the file or the ref.
     Refused, each ending `OCIOriginMismatch` with a message that says which of the two fields and which rule failed (never the pattern): no pattern list at all, an unanchored pattern, `.*` or any wildcard, alternation, a character class or repetition, a flag, another issuer, another host, another repository, another ref (a tag, another branch). That is strict on purpose: a release pipeline that signs on a tag, or a subject that names a reusable workflow of another repository, is refused until the operator uses `NotRequired` or the build learns the shape, and the message names the form that passes.
   - **Not tied to a repository.** Where the verification is keyless cosign for a repository of another provider than `GitHub` (the subject format is that host's), cosign with a key (`secretRef`) or Notation, the executor cannot tell which repository the signer stands for. The object maps when it is verified, and the declaration is the only tie between the key and the repository (known limit (a)).
   - The Kustomization's `status.lastAppliedRevision` must equal `status.artifact.revision` (`RevisionMismatch`; the equality is of two strings from the cluster, as `AppliedFetched` at `fluxstatus.go:227`, with no tag parsing, since the OCI revision is not a Git revision).
5. The artifact must carry `org.opencontainers.image.source` and `org.opencontainers.image.revision` in `status.artifact.metadata`, and the revision must parse as `<branch>@sha1:<40 hex>` or `<branch>@sha256:<64 hex>` (`fluxstatus.ParseRevision`, `fluxstatus.go:187`). Otherwise: `OCIOriginUnrecorded`. The parser accepts both forms, but only a SHA-1 commit can be checked in step 6 while GitHub is the only ancestry provider; a SHA-256 one ends `OCIOriginUnrecorded` there.
6. The cross-check against the declaration:
   - The annotated source must equal the URL of the declared repository, or equal it with `.git` appended (the form `git config --get remote.origin.url` gives). For a `GitHub` repository the owner and repository names are compared with ASCII case folded, because GitHub treats them as case-insensitive and the settings hold them in lower case (`remediationsettings_types.go:77`), while a recorded remote or a CI repository name keeps the real case; the scheme and host must still match exactly. No other rewriting: not `ssh://`, not `git@host:`, nothing else.
   - The annotated branch must equal the repository's `targetBranch`.
   - The annotated commit must be the head of that branch or one of its ancestors (`AncestryChecker.IsAncestor`, `providers/delivery.go:191`, implemented for GitHub at `internal/providers/github/ancestry.go:39`, a read through the Git App the mapping already opens, `sourcemap.go:222`). The call is made as the operation `read the ancestry of the artifact's commit`. It starts with `read `, so it joins the bounded Git read wait (`gitReadFailure` takes any `sourcemap.RefusedError` and a `sourcemap.TransientError` whose operation starts with `read `, `list ` or `open repository `, `internal/controller/gitread.go:221-227`). The error classes are decided one by one, before the error reaches the resolver's `transient()` (`sourcemap/errors.go:61-72`), which keeps a refusal as a `RefusedError` and turns every other error into a retry:
     - `ErrInvalidCommit` (the GitHub adapter compares SHA-1 only and refuses a SHA-256 or malformed ID for good, `ancestry.go:40-42`): `OCIOriginUnrecorded`, the commit cannot be compared.
     - `ErrNotFound` (a 404 or 410 of the compare call, `statusError`, `internal/providers/github/client.go:521-536`): `OCIOriginMismatch`, the repository does not have the commit.
     - `ErrForbidden` (403) and `ErrRejected` (422) (`client.go:521-536`): a refusal. It stops the request as a refusal of any other Git read does: the resolver returns a `RefusedError` (`sourcemap/errors.go:61-72`) and the controller reads its class with `refusal` (`internal/controller/pullrequest.go:2212-2226`), whose reasons are `GitForbidden` and `GitRejected`. There is no `OCIOrigin*` reason for it and no retry, since a retry could not succeed.
     - Every other error (a network error, a rate limit, a 5xx): a retry, inside the bounded Git read wait. A failed read is never a verdict.
   - Any difference: stop, reason `OCIOriginMismatch`, no Git write. The message names which of the three differed and shows no URL. The `OCIRepository` is recorded with the other Flux objects the mapping reads (`d.seen`, `sourcemap.go:94-113`) and read again after the Git scan, so an artifact pushed during the scan makes the mapping a retry. It is part of `Result.Observed` too. At the merge the freshness check does not reuse the plan's cross-check: it maps the target again (`freshness.go:327`, `checkSource` at `:655`), which reads the `OCIRepository` as it is then and runs the same cross-check on the current artifact. An artifact pushed between the plan and the merge is therefore judged on its own: if it still matches, the plan is fresh; if not, the mapping no longer resolves and the plan is stale with `SourceChanged` (`freshness.go:680`). Only an `OCIRepository` that changes during that check makes it a retry: `recheckInputs` (`freshness.go:359`, `:430`, `:488-517`) compares the resource version of each observed object with the one the mapping read and fails with "changed while the plan was checked, checking again". The cross-check therefore never describes an artifact that is no longer the current one.
7. The build directory is made in two steps, never as one join. First `spec.path` is checked as for a Git source, with `repopath.Join(".", spec.path)` (`sourcemap.go:258`), which refuses a leading `..` and returns the clean path inside the artifact root. Then that result is put under the declared `path`. `repopath.Join(declared, spec.path)` is never called: it resolves `..` inside the declared prefix (`Join("clusters/prod", "../../other")` returns `"other"`, true), while Flux's kustomize-controller clamps `spec.path` inside the artifact root, so it would apply `clusters/prod/other` while the mapping scanned and patched `other/`, outside the declared path. A `spec.path` of `../x` or `../../x` ends `InvalidPath`, as for a Git source.
8. Then the rules of ADR-0012 go on as for a Git source: exactly one settings repository (the declared one), the policy's `repositoryRef`, the `targetBranch`, the build directory (below), the declaration found by the scan in it, the live value equal to the value in Git, `allowedPaths`. The base commit is the head of the branch, as today.

Reason names are the proposal; the builder may change a spelling in the code review, not the cases.

### 3. What is read, written and granted, and what never is

| | Read | Written | Granted | Never |
| --- | --- | --- | --- | --- |

| Settings | the declaration is written by whoever may write `RemediationSettings`, a cluster administrator | | | read from the status |
| Analyzer, verifier | | | nothing | `ocirepositories`. The analyzer's delivery status tool (`get_delivery_status`) is unchanged: it does not read an `OCIRepository` and the comparison with the plan's repository is made only on the executor's path (`Verifier.Verify`, not `StatusReader.Status`, `flux.go:125-149`) |

The grant is opt-in. The chart gets the value `executor.ociSources.enabled`, default `false`, which renders a separate ClusterRole and ClusterRoleBinding with the one rule; kustomize gets the same as a separate component, as the analyzer's module grants (`dist/chart/values.yaml:246-250`, `config/rbac/analyzer/modules/flux/kustomization.yaml:1`). The default install stays as narrow as today. The rules are pinned by the RBAC test tables (`test/rbac/rbac_test.go`, the rows of `gitrepositories` at `:482-499` are the model: executor `get` on `ocirepositories` allowed; executor `list`, `watch` and every write refused; analyzer and verifier refused on every verb) and by the chart tests (`test/chart/chart_test.go`, around `:966`): the ClusterRole and its binding render only with the value on, and the default render has no rule on `ocirepositories` for any identity. With the value off and an entry declared, the mapping ends with `OCISourceNotReadable`, and the lookup page tells the operator to turn it on.

### 4. How the invariants hold

1. **Model output is never authorization.** The declaration is settings written by an administrator, and the annotations are compared, not obeyed. Nothing from the artifact reaches the policy or the model. The plan digest still covers repository, branch, path and build directory (`freshness.go:683` compares them at the merge), so a declaration edited between the plan and the merge makes the plan stale (`SourceChanged`) through the mapping run again with the new settings. This does not work yet: the call at `freshness.go:661-666` passes only `settings.Spec.Repositories`. The build adds `OCISources` to `sourcemap.Input` and has freshness pass `settings.Spec.OCISources`. Without it every OCI request would go stale with `SourceChanged` at the merge and no OCI pull request would ever merge (it fails closed, so it is not a hole, but it is a failure).
2. **Closed catalog.** No new action, parameter or patcher. The action still changes one declared field of one manifest in Git.
3. **Git only.** The only write is the pull request the executor opens today, in a repository of `spec.repositories`, on a branch derived from the request, to the entry's `targetBranch`, in a file `allowedPaths` allows. The pipeline that builds the artifact (the workflow, the registry, the tags) is never touched, since the file must be a manifest the action's patcher accepts and a path the policy allows.
4. **Cluster input is untrusted.** The two annotations are input from a registry writer, so they are only compared for equality with values the administrator declared, and a difference stops the request. They are never used as a repository, a ref, a path or a URL, never put in a message in full (the message says which comparison failed), and never shown to the model. Branch and commit are parsed with the strict parser that also parses Git revisions (`fluxstatus.go:187`). They are read only from an artifact Flux verified against a signer the cluster's operator chose (section 2, step 4), unless that origin is declared `NotRequired`. The `spec.verify` fields are read as text and compared with a fixed rule, never evaluated as a pattern against another string.
5. **Idempotent.** The mapping adds no state. Branch names, markers and the pull request lookup do not depend on the source kind. A restart maps again and gets the same answer or, after a new artifact, a fresh one.
6. **Separate identities.** One new `get` for the executor only, cluster-wide like its `gitrepositories` rule (opt-in, off by default). The analyzer and the verifier get nothing. No registry credential, no Secret read, no new App permission. AGENTS.md invariant 6 is amended in the pull request that builds this, to list the grant and its chart value.

### 5. The artifact revision, the base commit, the merge receipt, the delivery check and the verification

Three commits are in play, and they are not the same thing:

- **The base commit** of the pull request is the head of the declared branch when the request is mapped. It is not the artifact's commit. The artifact may be older than the head (CI is slower than a push), so the mapping checks that the artifact's commit is the head or an ancestor of it, and relies on the existing value check (live value equals the value in Git at the head) for the field it will change. A change in a file between the artifact's commit and the head that touches that field makes the values differ and stops with `ValueMismatch`; one that does not touch it is harmless.
- **The merge commit** is recorded in the merge receipt exactly as today (`api/v1alpha1/remediationrequest_types.go:554-559`, `:596-604`, ADR-0030 section 1). Nothing about the receipt depends on the source kind.
- **The applied commit** for an OCI unit is the commit in the revision annotation of the artifact the Kustomization applied. The delivery adapter will compute it only when `lastAppliedRevision` equals the current `status.artifact.revision` of the `OCIRepository` the Kustomization names; it fills `AppliedRef` and `AppliedCommit` from the annotation, as it does from `lastAppliedRevision` for a `GitRepository` (`flux.go:236-237`). Then the existing comparison runs unchanged: the unit is `Applied` when that commit is the merge commit or descends from it (`delivery.go:146`, `:159-185`), and the table of ADR-0030 section 2 applies row by row. The same goes for `AttemptedCommit` on a failure.
- When `lastAppliedRevision` is not the current artifact, there is no commit to read, and the status is `Pending`: the executor never reads an older artifact's metadata (it is gone from the status) and never reads the registry.
- The artifact's source annotation must also name the plan's repository, compared by the executor where it knows the plan; an artifact of another repository is `Pending`, never `Applied`. The ancestry question is asked of the plan repository, so a commit it does not know cannot count either.
- A read of the `OCIRepository` that the API server refuses (403 or 401, `providers.ErrForbidden` from the adapter's `readError`, `flux.go:281-282`) ends the request at once with the reason `OCISourceNotReadable`, the one the mapping uses. It is not retried until the window or the grace period passes, which is what any other failed delivery read does today (`lastingCause`, `phases.go:383-397`), because a retry cannot succeed until someone grants the read, and a timeout would say the delivery was not seen when it was never looked at. The adapter returns the class; the controller adds `OCISourceNotReadable` to the lasting causes it ends at once. Any other failed read of the object stays a retry. Only the executor's `Verifier.Verify` makes this read; `StatusReader.Status`, which the analyzer's delivery status tool uses, is unchanged and gets no grant on the kind.
- The window is the same hour (`rollout.go:70`). CI must build and Flux must pull within it, or the request ends `DeliveryNotObserved` (limit (d)).

What clears a request is not the annotation. After delivery the verification reads the live field, and a value that is not the desired one ends `Inconclusive` with `ValueChanged` (ADR-0030 section 2, table row "A later commit overwrote the field"). An annotation that lies can make the delivery look applied, never make a wrong value clear. Today it could still end a request wrongly: an early `Applied` lets the verification read the live field before the merged change arrives, the field still holds the old value, and the request ends `Inconclusive` with `ValueChanged` at once (`phases.go:555-567`; the reason is final and its text says a later commit overwrote the field, `phases.go:689`, which is false here). The change that arrives later would never be verified.

**For an OCI unit that ending is deferred until the delivery window has passed.** A differing live value is a wait, not an end, from the applied time to the end of the window:

- The delivery check records, in the status write that records the applied time, that the applied commit came from an artifact annotation, so the verification decides from recorded state and does not read the Kustomization again. This is a new field of the request's rollout status (name for the build, see Open points).
- While the field differs and the window has not passed, the request stays in `Verifying`. It shows the condition `Configured` `False` with the reason `ValueNotYetObserved` (a proposal like the other reason names), whose fixed message says that the applied artifact names the merge commit and the live field does not hold the desired value yet, and when the wait ends (the window end). The live value is not copied into the status, as today (`phases.go:689`). The reconcile is requeued at the poll interval of the delivery wait (`pollAfter(windowEnd.Sub(now))`, `phases.go:337`), so a change that arrives late is seen, and the verification goes on as for any request: `Configured` `True`, the rollout and the clearing.
- The window is the one of the delivery check: `deliveryWindowEnd` (`rollout.go:321-332`), `deliveryWindow` (`rollout.go:70`) from the time of the move to `Merged` (`MergeReceipt.MergedAt`, set by the executor's own clock at the transition, `limits.go:764-776`), plus the time writes were paused. Both ends of the comparison are the executor's, so no two clocks are compared.
- When the window has passed and the field still differs, the request ends as it does today: `Inconclusive`, reason `ValueChanged` (`phases.go:565-567`). For an OCI unit the message says that the artifact applied named the merge commit and the field never held the value within the window, instead of "a later commit overwrote it", which would be a claim it cannot make. The change is then not verified, and the ending is final.
- A Git unit is unchanged: it still ends at once.

### 6. Behaviour at the edges

| Case | End state | Reason | Why |
| --- | --- | --- | --- |
| No declaration for the `OCIRepository` | `NeedsIntervention`, no Git write | `OCIOriginNotDeclared` | the repository and path cannot be known from the cluster; the message says what to declare |
| Declared, annotation differs (source, branch or commit not in the branch) | `NeedsIntervention`, no Git write | `OCIOriginMismatch` | the declaration and the artifact disagree about where the files live; a person decides which is right |
| Declared, artifact has no source or revision annotation, or one that does not parse | `NeedsIntervention`, no Git write | `OCIOriginUnrecorded` | see below |
| Declared, the executor may not read `ocirepositories` (at the mapping) | `NeedsIntervention`, no Git write | `OCISourceNotReadable` | permanent until the grant exists |
| The delivery check may not read the `OCIRepository` (403 or 401) | `Inconclusive`, at once, not at the end of the window | `OCISourceNotReadable` | a retry cannot succeed; a timeout would say the delivery was not seen |
| `spec.verify` unset, `SourceVerified` not `True` for the current generation (and `verification` is `Required`) | `NeedsIntervention`, no Git write | `OCISourceUnverified` | the artifact was not verified by a signer the cluster's operator chose |
| Keyless identity not an anchored literal naming the declared GitHub repository, its `targetBranch` and the GitHub issuer | `NeedsIntervention`, no Git write | `OCIOriginMismatch` | the executor does not evaluate another person's regular expression; the message says which field and which rule |
| An applied artifact, live field differs, window not passed (OCI unit) | stays `Verifying`, requeued | `Configured` `False`, `ValueNotYetObserved` | the artifact may claim the merge commit early |
| An applied artifact, live field differs, window passed (OCI unit) | `Inconclusive` | `ValueChanged` | final; the change was not seen to arrive |
| Object missing, not Ready, suspended, with `ignore` or `layerSelector`, applied revision differs | as for a `GitRepository` | `SourceNotFound`, `SourceNotReady`, `SourceOptions`, `RevisionMismatch` | the same rules, same reasons, same waits for a reconciling Kustomization |
| Ancestry call (operation `read the ancestry of the artifact's commit`): SHA-256 or malformed commit (`ErrInvalidCommit`), or commit unknown to the host (`ErrNotFound`) | `NeedsIntervention`, no Git write | `OCIOriginUnrecorded`, `OCIOriginMismatch` | permanent answers, never retried |
| Ancestry call: 403 or 422 (`ErrForbidden`, `ErrRejected`) | stops as any refused Git read | `GitForbidden`, `GitRejected` | a refusal is final, not a retry (`sourcemap/errors.go:61-72`, `pullrequest.go:2212-2226`); step 6 says the same |
| Any other read or ancestry call fails (network, rate limit, 5xx) | retried inside the bounded Git read wait, no stop | none | a failed read is never a verdict; the operation starts with `read `, so `gitReadFailure` counts it (`gitread.go:224-227`) |
| Other source kinds (`Bucket`, `ExternalArtifact`, `HelmChart`) | `NeedsIntervention` | `UnsupportedSource` | unchanged |

**An artifact without annotations is refused, not accepted on the declaration alone.** With the declaration alone:

- the executor would have no evidence that the artifact has anything to do with the declared repository, so a wrong declaration (a mistyped path, a repository that CI no longer builds from) would open pull requests that deliver nothing;
- it could not tell a delivered merge from an undelivered one, since the artifact's revision names no commit: every request would wait the full hour and end `DeliveryNotObserved`, which reads as a failure of Shadewright;
- the declaration would be the only guard, and the issue asks for the artifact as a second one.

A pipeline that does not record the annotations records them by adding `--source` and `--revision` to `flux push artifact`, which the CLI requires anyway.

## Consequences

Clusters that deliver through OCI artifacts can get pull requests. The cost is an explicit declaration per `OCIRepository`, an artifact pipeline that records its source and signs the artifact, and one more opt-in grant.

Known limits:

- (a) The annotations are accepted only from an artifact Flux verified (`spec.verify` set, `SourceVerified` `True`), unless the origin is declared `NotRequired`. What this proves is bounded. For keyless cosign on a GitHub repository, the executor checks that the signer identity is an exact literal naming the declared repository and its `targetBranch` (section 2, step 4), so the signer is a workflow of that repository on that branch. It does not read the certificate: it trusts that Flux enforces the pattern the operator wrote, and the Sigstore roots the operator chose (`trustedRootSecretRef`, or Flux's default). A signature made by a workflow on the right branch is still a workflow someone with write access to that branch controls. For cosign with a key, for Notation, and for keyless on a host other than GitHub, the executor cannot tie the signer to the declared repository: whoever holds the key, or the identity the operator accepted, can sign annotations that match any declaration. And with `verification: NotRequired` anyone who can write to the registry can set them to match. In all these cases the annotations are a cross-check against mistakes and drift, not authentication, and what bounds a forged artifact is the value check against Git, the render check and the review of the pull request.
- (b) CI may change the files between Git and the artifact (a substitution step, a generated overlay). The mapping compares only the one field it will change. Another difference is invisible to it. So is a file CI leaves out of the artifact with `--ignore-paths` or `--add-ignore-paths`, or that source-controller leaves out (section Context, last upstream bullet): a declaration in such a file is found in Git by the scan and does not exist in what the cluster applies.
- (c) For an OCI unit, "applied" rests on an annotation, which is cluster-side input, where for Git the commit comes from Flux. An artifact that names the merge commit and the plan's repository early makes the delivery look applied. This is decided, not left open: an applied OCI unit whose live field differs from the desired value stays `Verifying` and waits for the value until the delivery window has passed (section 5). The request shows `Configured` `False` with the reason `ValueNotYetObserved` while it waits, and it ends `Inconclusive` with `ValueChanged` when the window passes with the field still different, with a message that does not claim a later commit overwrote it. What remains is the cost: a value that really was overwritten by a later commit is also waited for, up to the window, before the request ends, and a forged annotation can delay an end that would otherwise be at once. It cannot make a wrong value clear.
- (d) The artifact is built after the merge, so the one-hour window includes the CI run and Flux's poll interval. A slower pipeline ends `DeliveryNotObserved` with the change possibly delivered later.
- (e) The delivery is read only while the applied artifact is the current one. Two artifacts in quick succession can leave no moment where the merge commit's artifact is both applied and current. The later one descends from the merge commit and counts. A Kustomization that applied an artifact that is then replaced and never applies another one shows `Pending`.
- (f) The source annotation is compared as a string. A pipeline that records an `ssh://` or `git@` form never matches until it records the HTTPS form. Case is folded for GitHub names only (section 2, step 6).
- (g) A wrong `path` that still finds one declaration with the right live value opens a pull request in the wrong directory. The render check of the pull request step runs on the build directory the path implies, so it fails when that directory does not build to the same objects; it does not prove the path is the right one.
- (h) `kubectl shadewright doctor` and the analyzer's `get_delivery_status` compare only with a `GitRepository` (`fluxrules/flux.go:190-194`). They keep reporting an OCI source as not compared until a follow-up teaches them, and the analyzer's Flux grant is not widened here.
- (i) The list the mapping copies (`internal/gitops/repopath/generate.go:38-43`) is source-controller's list for a `GitRepository` (fluxcd/pkg `sourceignore`). Source-controller's OCI exclusions and the `excludeOCI` default of `flux push artifact` are separate lists upstream. The builder compares them with the copied one before it reuses it for an OCI source; a difference is a bug in the build, not a decision. A file excluded by CI's `--ignore-paths` is covered by limit (b).
- (j) A declared `OCIRepository` whose `spec.url` is later pointed at another artifact keeps its declaration. The annotations are still compared on every mapping, so another origin ends `OCIOriginMismatch`, but a pipeline that copies the annotations passes. With verification `Required` the new artifact must also verify against `spec.verify` as it stands, and for keyless GitHub signatures the identity rule names the declared repository, so the copy has to be signed by a workflow of that repository.

## Alternatives considered

- **Option 1, the declaration alone.** Explicit, and no trust in the artifact. But nothing ties the artifact to the declared repository, and the delivery check could not work: the revision of the artifact is no commit, so every request would end `DeliveryNotObserved` or need a second mechanism to tell a delivered merge. Refused for the reasons of section 6.
- **Require verification** (adopted, section 2, step 4). The annotations are read only from an artifact Flux verified, so what the cross-check compares comes from a signer the cluster's operator chose, and for keyless GitHub signatures the signer is tied to the declared repository. The cost is that clusters that do not sign their artifacts cannot use this until they sign or declare `verification: NotRequired`, and the strict identity rule refuses patterns that are loose or that name a tag or a reusable workflow. It adds no read beyond `spec.verify` and two conditions. A looser reading of the operator's regular expressions (accepting a prefix, or testing whether it would match the repository's name) was rejected: evaluating a pattern someone else wrote against a string chosen by the executor says nothing about what the pattern accepts.
- **Trust the annotations alone.** Rejected: that is option 2 below with a cross-check that proves nothing, since the annotations are set by whoever writes to the registry.
- **Option 2, the annotations alone.** The annotations do not say the path, so the path would have to be guessed. They are also set by whoever writes to the registry, so a registry writer would choose where a pull request goes, within the repositories of the settings. That is invariant 4 turned around: input from outside decides a destination.
- **A `GitRepository` kept next to the `OCIRepository`, used only for the mapping.** The mapper could then reuse every Git rule. But the Kustomization does not deliver from that `GitRepository`, so its `lastAppliedRevision` and Ready say nothing about it, and nothing would tie it to the artifact that is applied. The cluster would also fetch a repository only to give the executor a URL, with credentials for it, and the mapping would pass for a source that is not the one in use. It trades a declaration in the settings for an object in the cluster that proves less.
- **Declaring a branch.** See section 1: it can only repeat or contradict `targetBranch`.
- **Reading the artifact's content from source-controller.** It would let the mapping read the files that Flux applies. It needs a network path and a grant to source-controller's artifact server, widens the executor's reach much further, and gives content that is again from the cluster side. Not taken.

## What is to be built

1. API: `spec.ociSources` with its CEL rules (including `verification`, default `Required`), generated manifests and CRD docs; the settings reference page; the new field of the rollout status that records an applied commit taken from an annotation.
2. Mapping: `fluxrules` rules for an `OCIRepository` source, the new reasons (among them `OCISourceUnverified`), the declaration, the verification and identity rule (step 4) and the ancestry check in `sourcemap`, the freshness check with the new input (`sourcemap.Input.OCISources`, passed from `settings.Spec.OCISources`), with the `OCIRepository` recorded in `Observed`, read again after the scan and rechecked by freshness; the reasons added to the metrics list (`internal/controller/metrics.go:155`) and to the explain table (`cmd/kubectl-shadewright/explain.go:255`).
3. Delivery: `AppliedRef` and `AppliedCommit` from the annotation of the current artifact, the plan repository check, `Pending` otherwise; the read of the `OCIRepository` only in `Verifier.Verify`; `OCISourceNotReadable` among the lasting causes that end the request at once; the wait of section 5 in the verification step (`ValueNotYetObserved`, the end as `ValueChanged` once the window has passed).
4. RBAC: the opt-in ClusterRole in the chart and as a kustomize component, with the RBAC and chart test tables of section 3; AGENTS.md invariant 6, the threat model and the design document updated with the grant.
5. Docs: the reasons page (`docs/reasons.md`), the delivery table of `docs/troubleshooting.md` (its `UnsupportedSource` row says "Use a Git source"), the how-it-works source mapping page, a how-to for declaring an OCI source and for `flux push artifact --source --revision`.
6. Tests that fail without the change: one per reason, the 403 case, the retry cases, a forged annotation that names another repository, and a lab run with an artifact pipeline. Also: a `spec.path` of `../x` and of `../../x` under a declared path that ends `InvalidPath` (it fails against `Join(declared, spec.path)`); a SHA-256 annotation ends `OCIOriginUnrecorded` and a 404 on the ancestry call ends `OCIOriginMismatch`, each with no requeue; a mixed-case annotation of a GitHub repository matches; the `OCIRepository` changing `resourceVersion` mid-scan is a retry; an envtest case where an OCI request stays fresh across an unrelated merge and goes stale when the declaration's `path` or `repositoryRef` changes. For the decisions of section 2 and 5, each failing without its change:
   - Verification: an `OCIRepository` without `spec.verify`, one with `SourceVerified` `False` (`VerificationError`) and one whose condition has an old `observedGeneration` each end `OCISourceUnverified`; with `verification: NotRequired` the first maps. Identity table, one case each, all `OCIOriginMismatch`: an unanchored subject, a subject with an unescaped `.`, `.*`, an alternation, `(?i)`, a repository prefix (`repo-evil`), another owner, another ref (a tag), another issuer, an empty `matchOIDCIdentity` list, and two entries of which one is loose. The accepted case passes, with owner and repo in another case. A key-based and a Notation verification map and are not identity-checked.
   - Ancestry, one test per class, each with no requeue unless it is a retry: `ErrInvalidCommit` gives `OCIOriginUnrecorded`; `ErrNotFound` gives `OCIOriginMismatch`; a 403 and a 422 stop with `GitForbidden` and `GitRejected`; a 5xx, a rate limit and a network error retry, and a failed attempt counts toward the bounded Git read wait (the operation name starts with `read `).
   - Freshness: an artifact replaced between the plan and the merge by one that matches the declaration leaves the plan fresh; one that does not makes it stale with `SourceChanged`; one replaced while the check runs makes it a retry.
   - Delivery: a 403 on the `OCIRepository` ends the request at once with `OCISourceNotReadable`, where a 403 on a `GitRepository` stays as today; the analyzer's delivery status tool reads no `OCIRepository` and the analyzer has no grant on the kind.
   - Early artifact: an applied OCI unit with the old value stays `Verifying` with `ValueNotYetObserved` until the window passes, goes on to `Configured` when the value arrives, and ends `Inconclusive` with `ValueChanged` and the OCI message when the window passes; a Git unit with the old value still ends at once.
   - RBAC: the executor `get` on `ocirepositories` only, with the value on; no rule for any identity with it off; nothing for the analyzer and the verifier either way.
