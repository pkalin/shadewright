# ADR-0023: How the analyzer calls the model: prompts as code, context first, one structured call

- Status: Accepted
- Date: 2026-11-03

## Context

The analyzer is the only component that talks to a model, and everything it sends is partly attacker-controlled: events, logs, annotations and Git files may carry prompt injection ([ADR-0003](0003-gitops-only-typed-remediation.md), invariant 4). Several choices about that call are still open, and the tasks for it ([#70](https://github.com/pkalin/shadewright/issues/70) context builder, [#74](https://github.com/pkalin/shadewright/issues/74) read tools, [#76](https://github.com/pkalin/shadewright/issues/76) analysis loop, [#79](https://github.com/pkalin/shadewright/issues/79) injection corpus) depend on them:

- Where prompts live and who may change them. A prompt decides what the model is told about its role, the action catalog and the output format, so whoever can edit it influences what gets proposed.
- Whether the model explores the cluster with tools from the first step or receives a prepared context. Free exploration makes cost and latency per incident unpredictable and hard to replay in tests.
- When a stronger, more expensive model is used, and what triggers it. Anything the model writes, including its own list of missing data, can be steered by injected text, so it is a poor trigger.
- How a change to a prompt, model or schema is shown to be safe before it ships, and how the running analyzer knows it is using a combination that was shown to be safe.

[ADR-0013](0013-adapters-for-every-external-system.md) already puts the model behind `ModelProvider`, and [ADR-0015](0015-analysis-records-outlive-the-lab.md) stores one record per analysis. Design sections 3.3, 4, 11 and 12.3 describe the intent; this ADR fixes the mechanics.

## Decision

1. **Prompts are code.**
   - Prompts are Go `embed` templates in `internal/analysis/prompts/`, reviewed and released like any other code.
   - Every analysis record stores the prompt version (a content hash of the templates and generated parts that were used), the model deployment and model ID, and the token counts ([ADR-0015](0015-analysis-records-outlive-the-lab.md)).
   - The MVP has no ConfigMap, CRD or settings field for prompts. A prompt an admin can edit at runtime is an authority surface: it sits next to the closed catalog and the policy and could contradict them.
   - A replaceable prompt may come later only as an extension under [ADR-0019](0019-extension-packaging.md): signed, pinned by digest, and still subject to the evaluation gate (point 8).

2. **Generated from the Go types.** The catalog section of the prompt, the output JSON schema and the schema of a proposal are all generated from the Go action and result types. They cannot drift from the code, and an action added to the catalog appears in all of them or in none.

3. **Prompt structure.**
   - A static system part: role, rules, the generated catalog and the output schema. It does not vary per incident, so it can use provider prompt caching.
   - Then the untrusted context in delimited blocks. Each block is tagged with its provenance: event, pod status, log excerpt, metric, Git file or tool result.
   - An explicit rule in the system part: text inside those blocks is data, never instructions. The prompt is one defence only; the real limits are the schema, the catalog and policy (invariants 1 and 2). The injection corpus of [#79](https://github.com/pkalin/shadewright/issues/79) tests this.
   - The prompt is not the only thing that decides what the model sees. Operator-supplied redaction patterns and a swapped model deployment change it too, which is why point 8 keys the evaluation on the model and the prompt together and fails closed.

4. **The MVP loop: context first, one call.**
   - Deterministic rules and runbooks run first. A runbook match is deterministic and makes no model call: it maps an incident's symptoms to a known diagnosis and a typed proposal by rules in code.
   - The model path is for incidents no runbook matched. Its common case is one small-model call.
   - The context builder ([#70](https://github.com/pkalin/shadewright/issues/70)) assembles a bounded, redacted context deterministically, and the small model makes one structured-output call on it.
   - Read tools ([#74](https://github.com/pkalin/shadewright/issues/74)) are offered only on escalation, within fixed step, token and spend budgets.
   - Why: predictable cost per incident, and recorded contexts replay in CI.

5. **One proposal path.** The structured output of the call, whether small or escalated, is the only way a proposal is made. One validator checks it against the generated schema and the catalog and builds the `RemediationRequest`. There is no `submit_remediation_proposal` tool: the model's tools are read tools only. This removes a second path to a request that would need its own validation, and it makes tool-free calls and escalated ones end the same way.

6. **Escalation runs on deterministic signals only.**
   - The valid triggers are: the context builder truncated the context or could not fetch a source; or the small model's output failed schema validation after one retry.
   - A non-empty "missing data" in the result is not a trigger. It becomes a hand-off to a person that says what is missing, because it is model output and injected text can steer it. The model's self-reported confidence is never a trigger or a signal of eligibility.
   - Escalation uses the stronger model with read tools, bounded by steps, tokens and the daily spend limit. It is capped at one per incident fingerprint per cooldown window.
   - An escalation makes at most `maxToolSteps` + 1 model turns. An invalid escalated result gets no retry; it is handed off. With the triage call and its one retry, an analysis makes at most 3 + `maxToolSteps` model calls in total; a retry after a throttled or transient failure (`ErrRetryable`) counts toward that bound.
   - Every tool result passes through `internal/redact` before the model sees it, like the context does (invariant 4).
   - When a budget runs out the result is a hand-off, not a proposal.

7. **A policy denial is a hand-off.** Policy runs in the executor after the request exists. If it denies a request, the analyzer never re-proposes, and the denial reason is never shown to the model. Policy outcome is therefore not an escalation trigger, and the analyzer needs no new permission to read it.

8. **`ModelProvider` and the evaluation gate.**
   - Today's interface is built: `Complete(ctx, CompletionRequest) (Completion, error)`. A request carries messages, tool definitions, an optional `ResponseSchema` and `MaxOutputTokens`. A completion carries `Content string`, tool calls, `Usage`, `UsageUnknown` and a `Model` field. Throttling and transient failures (408, 429, 5xx, timeouts) are `ErrRetryable` errors; an unknown deployment is `ErrNotFound`, final.
   - Planned changes, made with the analysis loop: a deployment field on the request (so the record can name it); a typed error for timeouts, beside `ErrRetryable` (design 11.1). Foundry adapters for the OpenAI and Anthropic families, because the lab region offers both ([ADR-0016](0016-lab-region-sweden-central.md)): the OpenAI-format one is built (`internal/providers/model/foundry`, #75) and already returns malformed output as `ErrMalformedOutput` with the reply's usage; the Anthropic one is planned.
   - **What CI covers.** A change to a prompt, model or schema must pass the scenario evaluation before merge. In CI the evaluation runs against a fake model and covers plumbing, schemas and refusal paths only. It does not test the prompt's defences or the quality of any model.
   - **What gates quality.** A recorded real-model evaluation, keyed by model ID and version plus the prompt hash, stored in this repository (for example `test/eval/results/`). Its inputs are recorded contexts from the six fleet scenarios, kept here (for example `test/eval/contexts/`). The expectations are the fleet's `scenarios/*/expected.yaml` in `pkalin/shadewright-fleet`, and each result pins the fleet commit it read them from. The real model runs on demand.
   - **Fail closed at run time.** The analyzer embeds the list of evaluated (model, prompt hash) pairs that passed. It refuses automatic analysis when the model behind the configured deployment (and `Completion.Model` in a reply) has no passing record for the current prompt hash, and reports the reason in status and metrics. It then hands off instead of calling or trusting the model.

9. **Spend accounting.**
   - A failed or timed-out call is charged at its upper bound: the input estimate plus `MaxOutputTokens`, except a call the adapter marks as not processed (amendment 2026-11-15).
   - The daily count of analyses is kept in the operator namespace, in an object the analyzer owns: the ConfigMap `shadewright-analysis-budget` (the UTC day and the analyses started on it), shipped empty with the analyzer and checked by typed parsing in Go ([#43](https://github.com/pkalin/shadewright/issues/43), design 3.2). The analyzer may `get` and `update` that one ConfigMap, named in `resourceNames`, and may not create it, so deleting it stops analysis instead of resetting the count. Every write uses the resourceVersion read.
   - The daily spend limit is a count of tokens (input and output) per model deployment and UTC day, `maxTokensPerDay` in `RemediationSettings`, not an amount of money, so no price list lives in the settings ([#68](https://github.com/pkalin/shadewright/issues/68), design 12.3). Where that spend is counted is open ([#208](https://github.com/pkalin/shadewright/issues/208)).
   - A counter that is missing, cannot be read or written, or holds a value that cannot be trusted (a future day, a count out of bounds) means refuse, not allow.

## Consequences

- A prompt change is a pull request with a diff, a reviewer, a test run and a new evaluation record. Operator redaction patterns and a swapped deployment also change what the model sees; the evaluation list catches the deployment case by refusing an unevaluated model, and redaction changes are reviewed as configuration.
- The catalog, the schemas and the prompt cannot disagree, at the price of a small generator and its tests.
- The cost of a runbook match is zero, and the common model case is one call. Escalation is the only open-ended path, with its own budgets and a cap per fingerprint.
- A model that goes untested cannot run by accident: upgrading a deployment's model without a new evaluation record stops automatic analysis until one is added. That is intended, and it needs a recorded evaluation per model, which costs real-model runs and repository space.
- The fake model in CI cannot judge quality or injection resistance. Quality depends on the recorded evaluation being run when it should be.
- A fixed context may omit something the model would have fetched. Truncation and fetch failures escalate; "missing data" produces a hand-off that tells the person what to look at.
- Hand-off on a denial means the analyzer does not try again with a different proposal; a person decides what to do next.
- Admins cannot tune prompts for their cluster without a new release or, later, a signed extension. That is intended.
- Prompt caching depends on the provider and the deployment type; the structure allows it but does not require it.
- The analyzer gains one write beyond Incidents and requests: `update` on its budget ConfigMap. Invariant 6 in `AGENTS.md` names it. Whoever may write that ConfigMap (the analyzer, admins) can reset the count, and whoever may create ConfigMaps in the operator namespace can recreate it after a deletion (threat model, section 6).

## Alternatives considered

- **Prompts in a CRD or ConfigMap:** easy to tune, but anyone with edit rights on that object would influence what the model proposes, outside code review and the evaluation gate. Rejected for the MVP.
- **A full agentic tool loop from the start:** flexible, but cost and latency per incident vary widely, the prompt sees attacker-controlled tool results at every step, and runs are hard to replay. Kept only as the escalation path.
- **MCP as the tool layer in the MVP:** design 4 keeps MCP optional. It adds a protocol and a trust boundary without replacing RBAC, and the tools are few and fixed. Revisit with the extensions stage.
- **The model's confidence, or its list of missing data, as an escalation or eligibility signal:** both are model output that injected text can steer, and confidence is not calibrated. Escalation uses deterministic signals, and eligibility uses policy (invariant 1).
- **Feeding the policy denial back to the model for a second proposal:** it would show the model the policy's shape and let it search for a proposal that passes. Rejected; a denial ends in a hand-off.
- **A `submit_remediation_proposal` tool beside the structured output:** two paths to a request, each needing validation. Rejected for one path.
- **A money cap in settings:** rejected, it needs a price list in the settings that goes stale. The cap is in tokens per deployment (decision 9).
- **A filter of terminal escape sequences at display time** (amendment 2026-11-17): it would have to know what each terminal does with a sequence, a backspace or a carriage return. A grammar of terminal behaviour is a list, and reviews kept extending it; it also protects only the displays that use it, not a raw `kubectl get -o jsonpath` or a log reader. Rejected for removing control characters where model output enters the loop.
- **Refusing every reply that holds a Cc control anywhere as `InvalidOutput`** (amendment 2026-11-17): it would remove the clean/refuse split of the result's fields and the path walk that reports where a control was. Not taken: a whole diagnosis would be lost for one stray control in prose (a model copying a log line), and after a refusal in escalation there is no second attempt. The cost accepted instead is the per-field declaration, guarded by the reflection test that refuses an untagged field. No recorded reply holds a control, so the choice is not measured.

- 2026-11-17: Model output is untrusted input, so decision 5's validator never accepts a control character. These rules apply where a reply of any provider enters the analysis loop, once, before anything is parsed, redacted, stored, logged or compared; a control character is a code point of Unicode category Cc (C0, DEL, C1) other than newline and tab. **Free text is cleaned:** the controls are removed from every decoded string of a free-text field of the result (the summary, the hypotheses, the evidence quotes, the missing data, the uncertainty, the expected effect), and the rest is kept. **Every other field refuses:** a control in a field that is an enum, a pattern or an identifier (the action type, the container, the memory values, the evidence source, the verification checks) or in an object key ends the result as not matching the schema, as the same value did before, because removing it could turn a value the validator refuses into one it accepts and a request would name what the model never wrote. The split is declared by field next to the result type, and a field added later is refused until it is declared free text. Only decoded strings are cleaned, never the JSON text, so a raw control between two escapes cannot join them into another character, and text JSON refuses (a raw C0 control inside a string) stays refused. No Cc control reaches storage, so the rest of an escape sequence and letters a backspace or a carriage return would hide stay visible. Format characters (Unicode category Cf: bidi overrides such as U+202E, zero-width characters) are not removed: they can reorder or hide text on a terminal that renders them, and only the kubectl plugin removes them for display. They stay in storage because zero-width joiners and direction marks are part of ordinary text in some scripts. **A tool call is refused:** a call whose name, ID or any decoded argument string or key holds a control character is not run, since removing it could turn a value that would be refused into one that is accepted (`sh` ESC `op` as a namespace into `shop`). Its tool result is a fixed text saying it held control characters, it uses its step as any refused call does, what is logged or recorded about it is the cleaned form, and the analysis record counts it (`toolCallsWithControls`). The provider blocks (the Anthropic adapter's replay of the reply) go back unchanged, so the model sees the call it wrote with a result that says it was refused. The alternative, a filter of terminal escape sequences at display time, was rejected: a grammar of terminal behaviour is a list that reviews kept extending, and it leaves text printed raw unprotected. Through the built adapters only arguments reach the tool-call refusal: a control in a tool name or ID fails the adapter's own check first, and the whole reply is malformed output. **The context is shown the same way:** the same control characters are removed from the cluster text the model is shown (context blocks, tool results) and from a reviewer hint, so the text shown, the parts a quote may cite and a cleaned quote agree. Redaction decides first, on the text as it was read, and also reads that text as it will be shown, without its controls (the redactor's controls view), so a key or a token that removing a control would join (`pass` ESC `word=`) is hidden by that one decision; the controls are then removed from the decided text, which takes away no marker. The text is never cleaned before the decision: a control can be the indentation or the line end that places a value in a block, and a decision on cleaned text would show values the decision on the text as read hides. Decided 2026-11-17 on [#834](https://github.com/pkalin/shadewright/issues/834) and [#852](https://github.com/pkalin/shadewright/issues/852) (the result's fields and the context in a second decision the same day); built in #852. Nothing else changed.

- 2026-11-21 ([#952](https://github.com/pkalin/shadewright/issues/952), [#1005](https://github.com/pkalin/shadewright/issues/1005)): decided, not built. Decisions 3 and 4 say the context builder gives the model a bounded, redacted context from blocks tagged with their provenance; they do not list the fields. The sections are in [design 3.3](../design/3-observation-and-deduplication.md#the-context-builder), and the object status section has shown only one resource field of a container, its memory limit. Blind runs outside the lab showed what that costs: a readiness probe on a port nothing listens on, a Pending pod whose request was not shown, and a memory leak that read like a small limit. The maintainer decided on 2026-11-21 that the object status section also shows the fields below. Each case is read from a named field of the pod status, never from an event (the builder reads no events), and shows fields of the matched container of the pod and of the template container of the same name, and no others (the one exception is the Pending row, which shows every container of the pod it names, and none from the template):

  - **What the status cannot tell.** A container whose last termination came from a failed liveness or startup probe is not a case: the pod status records the exit (reason, exit code, signal) but not what caused it, and the probe failure is only in an event, which the builder does not read. So a container that is restarting after failed liveness probes shows its probes only while it is running and not ready. A container that is waiting (for example in `CrashLoopBackOff`) matches no case. A running container that has not passed its startup probe is not ready, so it is covered by the first row, and a sidecar that is running and not ready matches like a regular container. Known limit, not built here: a container restarted by a failing liveness or startup probe that is ready in between (for example one with only a liveness probe, which waits in `CrashLoopBackOff` between kills) matches no case, so a liveness probe on a port nothing listens on, with no readiness probe, shows no probe. [#1005](https://github.com/pkalin/shadewright/issues/1005) does not cover it.
  - **The Pending row.** One line per container: the regular containers, the init containers and the sidecars, each marked, with requests next to limits, then the pod's `spec.overhead` and its pod-level `spec.resources` when set. No total is computed and no formula is written here: the scheduler's request is the scheduler's, and the lines let the model read it next to the message in the pod's condition. The row shows no template requests.
  - **No new read or grant, and why this amendment may decide it.** [ADR-0021](0021-amending-accepted-adrs.md) says an amendment never widens "what is allowed, granted or refused" on its own authority. What the model may see is a case of "allowed", so this needs an argument, not a pass. The fields come from objects the builder already gets: the pod template of the Deployment or StatefulSet it reads by name with its UID (`internal/incidentcontext/resolve.go`), the pods of the target it lists through `Pods` (`resolve.go`, `status.go` `podLines`), and the Incident it is given (`status.go` `summaryBlock`). The builder already shows other fields of those objects (`templateLines`, `containerLine`, `state`), and `get_resource`, on escalation, already returns the whole pod spec of a Pod, Deployment, StatefulSet or ReplicaSet, probes and ports included (`podSpec` in `internal/tools/kube.go` copies the spec and hides only the literal environment values), redacted and within 16 KiB, under accepted decision 4 of this ADR (read tools on escalation). So these fields are not new to the model; what changes is that the first call shows the few that the case needs. No RBAC rule, flag, tool or API call is added (invariant 6). And no field shown is a free-text field made to hold credentials: numbers, enums, a port number or name, and the HTTP path of a probe. The fields that are made to hold them, command and args, and the command of an exec probe, are not decided here. [#1078](https://github.com/pkalin/shadewright/issues/1078) takes them with their own ADR.
  - **Same redaction and bounds.** Each value goes through `Builder.value`, which redacts it and leaves it out whole, never cut, above `maxValueBytes` (1 KiB). The section text is redacted again as a whole and cut to its bound in whole lines, keeping the head (`Builder.finish`, `DefaultStatusBytes`, 8 KiB). The fields are untrusted cluster data (invariant 4): a tenant writes a probe path and a port name, so they can hold text aimed at the model, and are tagged and quotable like the other values of the section. A longer section means the cut can reach the pods with less trouble: the section keeps the target first, then the pods with the most trouble, and a pod Pending with `PodScheduled` false for reason `Unschedulable` counts as trouble, so it sorts before the healthy pods (today `troubleOf` scores only container statuses, so such a pod, which has none, sorts by name among the healthy ones and can fall outside `MaxPods` or the cut). Three rules keep the new lines from pushing out the evidence of the case itself: probe lines come after the pod's own condition and container state lines, not before; the pod's probes are shown only when they differ from its template's, so the pod lines of replicas of one revision do not repeat them; and the bounds are per container, at most 16 declared ports then one fixed line written by code (`(N more ports)`), and an HTTP path of at most 256 bytes (left out whole above it, never cut), and at most 3 matched container names, then one fixed line written by code with the number left out. The size is computed from the field sizes of one probe line, `    readiness httpGet port 65535 scheme HTTPS path <path> period 3600s limit 3600s success 100 failure 100`: 100 bytes of fixed text, 256 of path and 1 newline, 357 bytes. Three probes make 3 x 357 = 1071 bytes, with a 39-byte container heading 1110 bytes, a little over 1 KiB; the 16 port lines (`    port 65535/SCTP name abcdefghijklmno`, 41 bytes each with the newline, 656) and the 23-byte line `    (99999 more ports)` add 679, so one container's lines are at most 1110 + 679 = 1789 bytes, of the 8 KiB. That is a ceiling for one container of one object; the pod and its template, for 3 names, would reach about 6 x 1.8 KiB, which is why the number of containers is capped and why the pod's probes are left out when they equal the template's. The test below measures it with real lines. A redaction miss on a path (a secret in a path segment) is the residual risk of this amendment: it is a short value the tenant chose to put in a probe, and it is bounded.
  - **A tenant can trigger a case.** Anyone who can run a pod in a watched namespace can make a container not ready, a pod unschedulable or a container OOMKilled. That shows the fields of that pod, in that namespace, and of its own template: nothing of another pod or namespace, and nothing the tenant could not already read from its own objects.
  - **Node allocatable is not shown.** The analyzer may list Nodes only to detect the platform ([design 2.2.2](../design/2-architecture.md), `internal/analyzer/detection`; invariant 6). Using that list as model input is a different use of the read, with its own size and redaction questions (node labels, addresses and names are cluster-wide data the incident does not name). It needs its own decision. A Pending pod therefore gets its requests and the scheduler's message in the pod's condition, not the node's free memory.
  - **Instance lifetimes, what is read today.** The pod status keeps one terminated instance per container, so its start and finish times give the lifetime of the last instance only; that is shown today as two timestamps, and the amendment adds the computed duration. The Incident's `status.occurrences` keep the finish time of each earlier kill (`began` of a `termination:` record, at most 32) but no start time, and the context builder does not show them today. The Killing and BackOff events that #1005 names are read by the collector, not by the context builder. So the collector also records the start time of each terminated instance in its occurrence record (an optional `started`, from the same terminated state of the pod status its finish time comes from; decision of 2026-11-21 on [#1005](https://github.com/pkalin/shadewright/issues/1005)), and the Incident's summary lines show the age at the kill of at most the last 5 instances that have both times (not the object status section, which shows only the instance the pod status holds). `started` is written only on a termination record and never after its finish time: the collector leaves it out otherwise, and the schema refuses a record where it is after `began`. An instance without a usable start time (none, or one after its finish) is counted, not guessed: no age is computed from the time between two kills, which includes the restart back-off. A termination record names no container (its id is a hash of the pod UID, the container and the termination). The fingerprint of an OOMKilled Incident holds one owner workload and, through the note, one container name, and no pod. So the earlier ages are those of one container name across every pod of the workload and across template revisions (a limit raised by hand included), interleaved by finish time: a mixed series, which can look like a leak or hide one. The summary labels it that way in a fixed line, and recording a short pod hash with `started` to group the ages per pod is left to [#1005](https://github.com/pkalin/shadewright/issues/1005). The age of the matched container's last instance comes from its own pod status. The earlier ages are lines of the Incident's summary, under its own provenance (what the analyzer counted), written by code and not quotable, like the absorbed tally; the computed age in the status section is not quotable either, as its timestamps are not today. Where the write lives: the collector carries `started` on the Observation, and the Incident controller stores it in `status.occurrences` with the finish time (`internal/incidents`); none of it exists yet.
  - **Evaluation.** [ADR-0025](0025-analysis-claims-units-and-evaluation-manifest.md) decision 3 puts the context builder's version and limits in the evaluation manifest, so a change to it needs a new real-model run. The recorded scenarios are run before the change and again after it, on the same models and prompt hash, and the results are compared per scenario before the builder's branch merges. The builder's branch has to show the run, as ADR-0025 requires. Its tests have one case per row of the table, one in which a sibling container shows nothing, and cases that carry text aimed at the model in a probe path and a port name and are checked against the redactor and the bounds, plus cases for the points above: a template with hundreds of ports keeps the most troubled pod's state line; 40 healthy replicas and one Unschedulable pod whose name sorts last keep that pod; 256-byte paths on several not-ready containers at the 8 KiB bound keep every shown pod's condition and container state lines, and a pod with more than 3 not-ready containers shows 3 and the fixed line; `httpHeaders`, host, `grpc.service` and an exec command are never shown; two replicas whose earlier ages interleave are labelled as mixed.
  - Nothing else changes: the model still has no tool that reads more, escalation is still decided by code, and a policy denial is still a hand-off.

- 2026-11-22 ([#969](https://github.com/pkalin/shadewright/issues/969)): the object status section also shows that a pod is being deleted and when its grace period ends, and states it when the current exit of a container of that pod finished after the deletion began. The maintainer decided this on 2026-11-22. Like the fields of 2026-11-21, it is read from the pod and shown in the object status section ([design 3.3](../design/3-observation-and-deduplication.md#the-context-builder)):

  | Case, and the field it is read from | The section also shows | Fails |
  | --- | --- | --- |
  | A pod being deleted: `metadata.deletionTimestamp` set | on the pod's line, `being deleted, grace period ends <deletionTimestamp>`. No request time is computed or shown: a later delete whose shorter grace period would already have ended sets the `deletionTimestamp` to the time of that delete, with a period of 0 or 1 (the kubelet's final delete), so the timestamp minus `metadata.deletionGracePeriodSeconds` is then the start of the last grace period, not the time of the request | none: a timestamp written by code |
  | The current exit of a container of that pod: `status.containerStatuses[].state.terminated` (or `initContainerStatuses`), with a non-zero exit code, a reason other than `OOMKilled`, and `finishedAt` at or after the start of the last grace period (`deletionTimestamp` minus `deletionGracePeriodSeconds`, 0 when the pod has none) | the fixed note `exited after the deletion began`: the fact, with no conclusion about the cause. Such an exit does not rank the pod as troubled, and its log is not picked as trouble | open, and named: a real crash during the grace period (a segfault while the process flushes its data) reads the same, carries the same note and does not rank the pod |
  | A pod kept by a finalizer after a later delete whose shorter grace period had already ended (the kubelet's final delete, with a period of 0) | nothing more than the pod's line: the `deletionTimestamp` moved past the exits that finished before that delete, so they are not marked | open toward the behaviour before this amendment, and named: those exits are shown as failures and rank the pod as troubled |

  - **Why.** A rollout, a scale down or a node drain stops the containers of the old pods, for example with exit code 137 after the grace period or 143 for a runtime that exits on SIGTERM. Without the deletion, the model read those exits next to a real crash as failures of their own ([#969](https://github.com/pkalin/shadewright/issues/969)), and the old pod ranked among the troubled ones.
  - **No new read or grant, and why this amendment may decide it.** The pod is the one the builder already lists through `Pods` and describes in `podLines` (`internal/incidentcontext/status.go`); no RBAC rule, flag, tool or API call is added (invariant 6). `get_resource` on escalation (decision 4) returns a copy of the pod's metadata (`meta` in `internal/tools/kube.go`) that holds `deletionTimestamp` but not `deletionGracePeriodSeconds`, which the section now reads to decide the note. [ADR-0021](0021-amending-accepted-adrs.md) says an amendment never widens what is allowed on its own authority, so this needs an argument: the grace period is a number in an object the builder has already read, used by code to compare two timestamps, and never shown as a value of its own. The model sees a fixed note written by code and a timestamp it could already get, and nothing of another object.
  - **Two clocks.** The start of the grace period comes from the API server's clock and `finishedAt` from the kubelet's; the builder compares them with each other, never with its own clock. A kubelet clock that runs behind can show an exit of the shutdown as a failure, one that runs ahead can mark a failure of the last seconds before the deletion by the same skew.
  - **Not shown.** The pod's finalizers, who or what deleted the pod, the time of the request, and its events (the builder reads none). A container still running past the grace period is shown as running, with nothing marked. An OOM kill, a last termination (an earlier instance) and a completed container (exit code 0) are never marked. For a container with a marked exit and a last termination inside the window, the log excerpt reads that earlier instance first.
  - **Evaluation.** [ADR-0025](0025-analysis-claims-units-and-evaluation-manifest.md) decision 3 puts the context builder's version and limits in the evaluation manifest, so this change needs a real-model run. It is the lab run of the release candidate before v0.6.0: the recorded scenarios are run on the same models and prompt hash as the run before, and the results are compared per scenario. The prompt golden (`test/eval/testdata/prompt.golden`) pins the changed prompt of the `replaced-pod` scenario until then.
