# ADR-0045: The failed review check on a pull request on another base

- Status: Accepted, amended; the widening amendment of 2026-11-20 is Proposed
- Date: 2026-11-20

## Context

Issue [#925](https://github.com/pkalin/shadewright/issues/925), built in pull request [#939](https://github.com/pkalin/shadewright/pull/939). [ADR-0043](0043-the-executor-follows-its-own-pull-request-to-any-base.md) lets the executor follow its own pull request when a person changes its base branch, and lists "check run" among the things it never does on another base. [ADR-0028](0028-reviewer-hints-through-the-pull-request.md) section 5 makes the check run `shadewright/review` the merge check of a pull request the executor opened, when reviewer hints are on (`--reviewer-hints`).

A check run belongs to a commit, not to a base. A passing check written while the pull request was on the target branch stays the latest check of its head after a person moves the pull request to another base. If the request then stops (its plan goes stale, it is cancelled, or it stops for another reason), nobody updates the check. A person can merge, on that old pass, a change the executor no longer stands behind, and moving the pull request back to the target branch does the same. The only fix is to complete the check as failed, which is a Git write on a pull request that is on another base. ADR-0043 listed that write under "never", so this decision widens a write.

[ADR-0021](0021-amending-accepted-adrs.md) says an amendment never widens what is allowed on its own authority: another accepted ADR has to decide it. The owner confirmed the widening in an issue comment on 2026-11-20 and decided the exact list of writes in a later comment of the same date, and neither is an ADR. So the write gets this ADR, accepted before #939 merges. ADR-0043 then links it in an amendment, and this ADR links back. ADR-0021 is not changed.

## Decision

[![With reviewer hints on, the failed check run shadewright/review is written on the recorded head and recorded Stale: when a stale plan, a cancel or a stop reads the request's own pull request open on another base; when a stale plan or a cancel reads it closed on another base; when a stale plan, a cancel or a stop reads it gone without a new installation of the repository; and at every look of a stopped holder that leaves the lock held, by its own pull request or by another open one from its branch, while no failed check shows last on the recorded head, whatever its own pull request is: open elsewhere, closed, merged on another base or gone. A look that settles nothing yet writes it too, also through a new installation of the repository. Whenever the pull request is not read open on the target branch the summary is a fixed variant that promises no close. Nothing is written with hints off, when the reads fail, by a stale plan, a cancel or a stop that reads the pull request merged on another base or gone after a new installation, or by a look that settled the lock through a new installation while a pull request other than the recorded one holds it. Pause, a target branch change, a gone repository or a failing Git host delay the write and are said in the condition ReviewCheckNotFailed. Never on another base: push, comment, merge, update of title or body. No new read and no new grant.](../assets/diagrams/review-check-other-base.svg)](../assets/diagrams/review-check-other-base.svg "Open full size")

**What is written.** One check run: name `shadewright/review`, conclusion `failure`, on the recorded head commit of the request's own pull request, with reviewer hints on. This is the exact list of cases that write it on another base, and there is no other:

1. A stale plan or a cancel reads the pull request by its number and finds it open on a base other than the target branch. The cleanup of the stale plan fails the check before each try of the close, and a cancel fails it before it tries the close.
2. A stop (the step that stops the request for a pull request open on another base, and every look of a stopped holder that reads its own pull request open there) reads it open on another base.
3. A stale plan or a cancel reads the pull request closed on another base (a person moved it, then closed it). A closed pull request can be reopened and merged, so the failed check fails closed: an old pass must not stay the last check of a head that can still merge.
4. A look of a stopped holder leaves the lock held, by the request's own pull request on any base or by another open pull request from the request's branch, and the Git host does not show the failed check last on the recorded head (read once `Stale` is recorded; before that the look writes without a read). The request's own pull request can be in any state: open on another base, closed on any base, merged on another base, or gone. The look writes whether or not an earlier write failed, so it does not wait for condition `ReviewCheckNotFailed`. A look that settles nothing yet (its reads were answered, but only a later look may conclude: the first look that finds the recorded number missing, or answers that disagree) leaves the lock held too, and writes the same way; it does not read which pull request holds the lock, so it writes through a new installation of the repository as well. A look whose reads failed writes nothing; the next look tries. The check belongs to the request's own commit on its own branch, not to one pull request: every pull request from that branch shows it, and an open one can merge on a pass written before the stop. This is the case that keeps the failed check from being covered by an older write.

5. A stale plan, a cancel or a stop reads the pull request gone: the Git host says the number is not the request's own, and a new installation of the repository does not explain it. The check is written on the recorded head all the same. After a new installation of the repository a stale plan, a cancel or a stop writes nothing for it, as before; the looks of a stopped holder follow case 4.

The executor then records state `Stale` for that head in the request's status, and the request never writes the check again, with any state. A failed write of a stop is not final: the stop goes on, the condition `ReviewCheckNotFailed` shows it, and the next look of the holder writes it again. A stale plan or a cancel whose write fails for a pull request read gone only logs it, and the write is tried again only while the request holds the lock (the looks in case 4); a stale plan whose pull request is read closed waits on `errStaleCheckPending`, and a cancel on `CancelPending` or ends with the Event `CancelCheckNotFailed`. A look of a stopped holder whose failed check is recorded first reads the latest `shadewright/review` check of the head, and writes the failed check again only when another state, or none, shows last.

**A pull request read gone gets the check.** The check run is written on the request's own recorded commit, never on another pull request's head, so it can only keep that commit from merging. Without it an earlier pass stays on that commit while another pull request from the request's branch is open, and that pull request could merge a stopped plan. A commit the host does not know fails the write. For a stop the condition `ReviewCheckNotFailed` shows it; for a stale plan or a cancel it is only logged. After a new installation of the repository a stale plan, a cancel or a stop writes no check for a pull request read gone, as before. A stale plan, a cancel or a stop that reads the pull request merged on another base writes none: after that merge a check prevents nothing on it. A stopped holder's look writes it all the same while the lock is held (case 4), since the pull request that holds the lock has the same head and can still merge it.

**Conditions.** All of them:

- Reviewer hints are on. With hints off the executor does not own the check and writes nothing.
- The pull request is the request's own recorded pull request, which the request still owns (no handoff, no handoff intent).
- The read found it open or closed on another base (cases 1 to 3), or gone without a new installation of the repository (case 5), or a stopped holder's look leaves the lock held (case 4). A stale plan, a cancel or a stop that reads it merged on another base, or gone after a new installation of the repository, writes no check, and a read that failed writes none either; the read is retried.
- The cause is a stale plan, a cancel or a stop.

Beyond the close that the finalizer of a deleted request makes (ADR-0043), these are the only writes to a pull request on another base.

**What it carries.** A fixed title and a fixed summary. When the pull request is not read open on the target branch (on another base, read gone, or a stopped holder's look while its own pull request is not open) the summary is a fixed variant that says nothing is closed there and that a person decides what to do with the pull request, so it promises no close. The summary of the stop is one fixed text that promises no close on any base. It holds one constant in the summary of a stale plan and of a stop: the stale reason of the plan, the phase the request stopped in, `ChangeRequestOnOtherBase`, or `ChangeRequestGone` for a pull request read gone. The summary of a cancel has no constant. The text never holds the base name, a branch name, a hint, a comment or any other text from the code host.

**What is read.** Nothing new. The read of the pull request by its number is ADR-0043's. The latest check of the head (`ReviewCheckRun`) and the read of the request live from the API server before the merge gate writes are ADR-0028's, as amended. The check is written to the recorded head, which the executor itself pushed or adopted.

**What is granted.** Nothing. The write is the check run of ADR-0028 and uses the App permission `checks: write`, which every token request already names.

**What is never done on another base.** No push, comment, merge, update of title or body, and no auto-merge, as ADR-0043 says. No check is written there by a stale plan, a cancel or a stop that reads the pull request merged or, after a new installation of the repository, gone; by a look that settled the lock through a new installation while a pull request other than the recorded one holds it; when hints are off; or while the kill switch pauses writes. A repository entry that names another target branch than the recorded one permits reads only, so it writes nothing either, and a repository that left the settings cannot be opened.

**How the failed check stays the last one.** The merge gate reads the request live before it writes a check, and writes nothing for a request that is stopped, released, being deleted or gone. When that read fails, the only check it writes is the downgrade of a pass (pending or failed over a success). A stop's failed check is therefore never covered by a check written from an older copy of the request, and a pass never goes on the head without a live read that worked.

**When a write fails.** A write that cannot be made is said in status, not dropped: the condition `ReviewCheckNotFailed` carries the cause (paused writes, settings that permit no write, a refusal or a failure of the Git host) and a Warning Event is recorded when it is set or its cause changes. The earlier check stays on the head until a write goes through, which is the state before this decision, not a new one.

**How the invariants hold.**

- Invariant 3: the write is a failed required check, which can only keep a change from merging. It pushes nothing, merges nothing, and does not bypass a check or change a protected branch.
- Invariant 4: the base name and every other host text stays out of the check run. The summary holds constants of the executor (the stale reason, the phase, `ChangeRequestOnOtherBase`, `ChangeRequestGone`). The head commit is a full object ID taken from the request's status, and the provider refuses any other value.
- Invariant 5: the recorded `Stale` state and the head are what find the work again. A lost status write makes the next look write the same failed run once more, which is harmless, and a restart does not open or close anything.
- Invariant 6: the executor is the only identity that writes it, with the permission it already has. The analyzer and the verifier gain nothing.
- Invariants 1 and 2 are not touched: no model output, no new action.

## Consequences

A pass written before a person moved the pull request no longer decides a merge once the request has stopped. The cost is one more write on a pull request on another base, a failed check run that blocks and cannot approve.

Known limits:

- (a) The check blocks only where the ruleset of that base requires `shadewright/review` with the Shadewright App as its source. The executor cannot verify a ruleset (ADR-0028 section 5). On a base without the rule, the failed check shows but stops nothing.
- (b) The check is on the recorded head. A person who pushes a new commit to the pull request gets a head with no run. A required check without a run blocks the merge (ADR-0028), but an unrequired one does not.
- (c) The write can be late or missing. While writes are paused, the settings entry names another target branch, the repository is gone from the settings, or the Git host fails or refuses the write, the earlier check stays on the head. The request says so in `ReviewCheckNotFailed` and tries again at its next look; a person must not merge on the earlier check. The looks run at `heldRecheckInterval` (10 minutes) while the request holds the lock, so the write has no bound of its own beyond that pace and the life of the lock. While the reads of the looks keep failing (condition `GitReadRetry` says so) no look writes the check, and `ReviewCheckNotFailed` does not say it is owed. On a head already recorded `Stale`, a look that cannot read the check records only the Warning Event `StoppedCheckUnread`, which goes when the Event expires.
- (d) A stale plan, a cancel or a stop that reads its pull request merged on another base writes no check: after that merge a check cannot prevent it, and ADR-0043 limit (b) stands. A stopped holder's look still writes it while the lock is held (case 4). A commit the host does not know fails the write of a gone pull request's check. A stop shows it in `ReviewCheckNotFailed`; a stale plan or a cancel only logs it, and it is tried again only while the request holds the lock.
- (e) A window between the read and the write. A person who moves the pull request again between the two gets the check on a pull request that is now elsewhere. A check run belongs to the commit, so it shows on every pull request with that head, including one on the target branch. That can only block.
- (f) The failed check is final for the request. Moving the pull request back does not clear it, and the request writes nothing else. A person who wants the change makes a new request.
- (g) A write for a pull request read gone is on the recorded head with no read that ties it to an open pull request: a gone read is a 404 or a number from another branch. A person who later opens a new pull request at that commit meets the failed required check and needs a new commit. This fails closed.
- (h) It does not make the lock follow a reopened pull request: that is [#940](https://github.com/pkalin/shadewright/issues/940).
- (i) A look that settles nothing yet does not read which pull request holds the lock, so it writes through a new installation of the repository too, where a look that settled writes nothing while a pull request other than the recorded one holds the lock. The write goes to the recorded commit by its full object ID: where the repository behind the new installation does not have that commit, the write fails and `ReviewCheckNotFailed` says so; where it has it, the failed check can only keep that commit from merging. This fails closed.

## Alternatives considered

- Write nothing. A passing check from before the move stays the last one, and a person can merge a change the executor stopped. This is the defect.
- Close the pull request on a stop. A person moved it on purpose, and closing it destroys their work. ADR-0043 already decided that a stop closes nothing on another base.
- Amend ADR-0043 alone. It would widen a write on the authority of an amendment, which ADR-0021 refuses.
- Write the check when a stale plan, a cancel or a stop reads the pull request merged on another base. It prevents nothing on that pull request and adds a write. The looks of a stopped holder do write it while the lock is held (case 4), for the pull request that holds the lock and can still merge the same head.
- Write only when the pull request is open on another base. A closed one can be reopened and merged on the old pass, and a stopped holder's own pull request can be closed while another from its branch is open on the same head.
- Write nothing on a pull request read gone. The check is on the request's own recorded commit, so it can only keep that commit from merging, and without it an earlier pass stays while another pull request from the request's branch could merge a stopped plan. A commit the host does not know fails the write, which the condition shows.

## Amendments

2026-11-20 ([#925](https://github.com/pkalin/shadewright/issues/925), the decision of that date that replaces the per-verdict rows for a stopped request's check with one rule). Status: Proposed. The Decision and the limits above already state what the code does with it; until this amendment is accepted, the text as accepted on 2026-11-20 is the decision, and #939 does not merge before.

This widens the failed-check writes of the accepted text:

- **Case 4 no longer waits for condition `ReviewCheckNotFailed`.** The accepted text wrote it at a look only while the failed check was still owed, as that condition said. Now each look that leaves the lock held writes it unless the Git host shows it last on the recorded head.
- **An own pull request merged on another base gets it.** The accepted text refused that write (cases 4 and 5, the conditions, limit (d), "What is never done on another base", and the rejected alternative). Now a stopped holder's look writes it while the lock is held, whatever its own pull request is: open on another base, closed on any base, merged on another base, or gone.
- **The trigger is a look that leaves the lock held**, by the request's own pull request on any base or by another open pull request from its branch. The accepted text wrote only while another open pull request from the branch held the lock. [ADR-0043](0043-the-executor-follows-its-own-pull-request-to-any-base.md#amendments) (entry of 2026-11-19, limit (e)) states the same trigger.
- **A look that settles nothing yet writes it**, and that look does not read which pull request holds the lock, so it writes through a new installation of the repository as well. The accepted text wrote nothing through a new installation for a pull request read gone. A look that settled the lock still writes nothing through a new installation while a pull request other than the recorded one holds it.

Why each new write fails closed. Every one is the same failed check run `shadewright/review`, with the stop's fixed summary that promises no close, on the request's recorded head commit, which the executor pushed or adopted. A failed check can only keep that commit from merging; it approves nothing, pushes nothing and closes nothing (invariant 3).

- Without the gate on `ReviewCheckNotFailed`, the worst case is one more failed check on a head that already has one, which changes nothing, or a failed check over a pending or passing one written after the stop, which is the defect this ADR exists for.
- After a merge on another base, the merged pull request cannot be stopped, but the pull request that holds the lock has the same head and can still merge it on a pass written before the stop. The check blocks that one; on the merged one it shows and decides nothing.
- With the request's own pull request holding the lock, the check is the stop's own write (cases 1 and 2) made again at a look.
- Through a new installation, the write names the commit by its full object ID. A repository without that commit refuses it, and `ReviewCheckNotFailed` says so; a repository with it can only have that commit blocked (limit (i)).

Further points of the same decision, which widen nothing:

- **No pull request from the branch holds the lock.** Only the stop's own write remains where the list above has one (the stop for a pull request open on another base, case 2, and the stop for one read gone, case 5). No look follows, and the case stays open only as limit (c).
- **A refused write** sets `ReviewCheckNotFailed` and is tried again at each look while the lock is held. A release of the lock ends the condition, and so does the write that records a merge of the request's pull request (also while a verification keeps the lock); either one logs at Info that a check written before the stop may stay on the head.
- A failed check written for a pull request read gone by a stale plan or a cancel has its own fixed summary, which says the pull request cannot be found and that nothing is closed, instead of the summary for another base.

Why: four review passes on #925 each found a new verdict that left a pass on a shared head after a stop (gone, the stop on gone, the gone write without a gate, and the request's own pull request closed while another holds the lock). A rule that reads the verdict can miss the next one; a rule that reads the lock and the head cannot. A fifth pass found that a look settling nothing yet left the check for the next look (seed 1456 of the Git waits model, which the fixed seed set now holds). [ADR-0021](0021-amending-accepted-adrs.md) says an amendment does not widen on its own authority, so this one stays Proposed until it is accepted as this ADR's decision.
