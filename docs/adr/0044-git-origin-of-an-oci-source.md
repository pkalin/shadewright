# ADR-0044: The Git origin of an OCI source is declared, and the artifact is only a cross-check

- Status: Proposed
- Date: 2026-11-19

## Context

Issue [#935](https://github.com/pkalin/shadewright/issues/935). The source mapping of [ADR-0012](0012-object-to-source-mapping.md) follows a Flux Kustomization to its `GitRepository` and refuses every other source: the request ends `NeedsIntervention` with `UnsupportedSource`. Many clusters deliver through OCI artifacts instead. CI builds an artifact from a Git repository (`flux push artifact`) and pushes it to a registry, and Flux pulls it through an `OCIRepository`. The desired state still lives in Git, but an `OCIRepository` says where the artifact is, not which repository, branch and path it was built from. Those clusters get diagnoses and issues, never a pull request.

Today's code, so the change is read against it:

- A Kustomization whose `spec.sourceRef.kind` is not `GitRepository` stops the mapping with `UnsupportedSource` (`internal/gitops/sourcemap/fluxrules/flux.go:93-95`; the reason is defined at `fluxrules/result.go:87-88`).
- Flux objects are read as unstructured objects, and only the fields the rules name are used (`flux.go:43-44`).
- A `GitRepository` passes only when it sets none of `suspend`, `ignore`, `recurseSubmodules` or `sparseCheckout` (`flux.go:63`), and tracks one branch (`flux.go:258`); the Kustomization must have applied the revision the source last fetched (`flux.go:307`, `internal/fluxstatus/fluxstatus.go:227`).
- The source URL must equal exactly one repository of the settings, that repository must be the policy's `gitOps.repositoryRef`, and the branch must equal its `targetBranch` (`internal/gitops/sourcemap/sourcemap.go:331-355`). The URL is never put in a message (`sourcemap.go:330`).
- The base commit of the pull request is the head of that branch, read from the Git provider at mapping time (`sourcemap.go:233`, `sourcemap.go:308`). The freshness check runs the mapping again with the settings' repositories and compares repository, branch, path and build directory, not the base commit (`internal/policy/freshness/freshness.go:651-666`, `freshness.go:683`).
- The executor's cluster-wide role has `get` on `kustomizations` and `gitrepositories` and nothing on `ocirepositories` (`config/rbac/executor/role.yaml:23` and `:36`, from the markers at `internal/controller/cache.go:57-58`; the chart's `dist/chart/templates/rbac/executor-role.clusterrole.yaml:24` and `:37`).
- After the merge, the delivery check reads a commit out of the Kustomization's `lastAppliedRevision` only when its source is a `GitRepository` (`internal/providers/delivery/flux/flux.go:154`, `flux.go:236-237`). The unit is `Applied` when that commit equals the merge commit, or descends from it by the ancestry answer (`internal/providers/delivery.go:146`, `delivery.go:159-185`).
- `delivered` (`internal/controller/rollout.go:619-671`) reads the target and asks the Flux adapter twice, and reports `applied` only when both answers are `Applied` for the same commit (`rollout.go:646-670`). Both checks after the merge call it, the one with `--verify-outcomes` (`internal/controller/phases.go:290`) and the one without (`rollout.go:240`). In the first, an applied answer records the applied time (`recordApplied`, `internal/controller/merge.go:436-443`), the target's generation and template hash and the applied commit (`phases.go:320-325`), and the request moves to `Verifying` with its deadline measured from the applied time (`enterVerifying`, `phases.go:485-488`).
- Until then the request waits: it is requeued at the poll interval inside the delivery window, one hour from the move to `Merged` plus the time writes were paused (`phases.go:336-337`; `deliveryWindow`, `rollout.go:70`; `deliveryWindowEnd`, `rollout.go:321-332`). Past the window a read that worked and showed no applied commit ends `Inconclusive` with `DeliveryNotObserved` (`phases.go:351-352`, `endDelivery`, `phases.go:433`). A read that kept failing ends `Inconclusive` with `DeliveryNotChecked` once the window and its grace of ten minutes have passed (`phases.go:353-361`, `endDeliveryNotChecked`, `phases.go:458-465`; `finalGrace`, `rollout.go:80`).
- A read of a Flux object that the API server refuses (403 or 401) comes back from the adapter as `providers.ErrForbidden` (`flux.go:281-282`). `lastingCause` does not list it (`phases.go:383-397`), so it is retried with backoff like any failed read (`deliveryRetry`, `phases.go:370-378`) and shows no cause on the request (`deliveryReadFailed`, `phases.go:403-415`).
- Once the request is `Verifying`, the verification reads the live field and ends the request `Inconclusive` with `ValueChanged` at once when it differs from the desired value (`phases.go:555-567`). The text says "a later commit or change overwrote it, so this change never ran as merged" (`phases.go:688-690`).
- `Verifier.Verify` (`flux.go:125-132`) is the executor's path; `StatusReader.Status` (`flux.go:149`) is the read the analyzer's delivery status tool uses, and stays as it is.

The last two points matter most. For an OCI source the Kustomization applies `<tag>@sha256:<digest>` of the artifact (upstream: the revision of an `OCIRepository` artifact is the tag and the digest of the OCI artifact, [source-controller spec, "Artifact"](https://github.com/fluxcd/source-controller/blob/main/docs/spec/v1/ocirepositories.md)). It names no Git commit, and the cluster applies an artifact CI built after the merge, never the merge commit itself.

This ADR widens a read (the executor reads `OCIRepository` objects) and the places a pull request can come from (a workload delivered through a declared artifact). [ADR-0021](0021-amending-accepted-adrs.md) says an amendment never widens on its own authority, so it is decided here and ADR-0012 gets only a pointer after acceptance. [ADR-0043](0043-the-executor-follows-its-own-pull-request-to-any-base.md) is the model: say what is widened, say what never happens, state the limits.

### What the upstream Flux API gives

Read from the current upstream documentation and source on 2026-11-19, not from memory (the repository vendors no Flux types, so there is no pinned version to read; the code reads `source.toolkit.fluxcd.io/v1`, `internal/fluxstatus/fluxstatus.go`):

- `OCIRepository` status carries `status.artifact` with `revision`, `digest`, `url`, `size`, `lastUpdateTime` and `metadata`, a map of strings "such as OCI annotations".
- When the artifact was created with `flux push artifact`, `metadata` holds `org.opencontainers.image.created`, `org.opencontainers.image.source` ("the URL of the Git repository containing the source files") and `org.opencontainers.image.revision` ("the Git branch and commit SHA1 of the source files"). The Flux CLI requires `--source` and `--revision` and documents `--revision="$(git branch --show-current)@sha1:$(git rev-parse HEAD)"` (`cmd/flux/push_artifact.go` in fluxcd/flux2). The CLI strips credentials from the source it records. An artifact pushed by another tool, or with another `--revision`, can carry any value or none.
- The status has no field that says which Git repository, branch or path the content came from, other than those annotations. Registry access would be needed for anything else, and the executor has none.
- `spec.ignore`, `spec.layerSelector`, `spec.suspend`, `spec.verify` and `spec.secretRef` or `spec.serviceAccountName` exist in the spec. Source-controller leaves out what its default exclusion rules and any `.sourceignore` file match when it archives the pulled contents, and `spec.ignore` overrides the defaults ([source-controller spec, "Ignore"](https://github.com/fluxcd/source-controller/blob/main/docs/spec/v1/ocirepositories.md)). CI has its own filter: `flux push artifact` takes `--ignore-paths` (default `excludeOCI`) and `--add-ignore-paths` (`cmd/flux/push_artifact.go` in fluxcd/flux2). A file either step leaves out is not in the artifact, whatever Git holds.
- `spec.verify` is `OCIRepositoryVerification` (`api/v1/ociverification_types.go:23-48` in fluxcd/source-controller at `main`): `provider` (`cosign` or `notation`), `secretRef` (cosign public keys or the notation trust policy), `matchOIDCIdentity` (a list of `OIDCIdentityMatch`, cosign keyless only, `issuer` and `subject` as Go regular expressions, `ociverification_types.go:70-83`) and `trustedRootSecretRef` (a Sigstore `trusted_root.json`, for a self-hosted Sigstore). Flux reports the result in the condition `SourceVerified`: `True` when the signature verified, `False` with reason `VerificationError` on a failure, which the controller retries with backoff. The condition exists only while `spec.verify` is set and carries the `observedGeneration` of the spec it judged (`api/v1/condition_types.go:35-40`, `:74-76`).
- The signature covers the artifact's digest, and the digest covers the manifest, so the annotations of a verified artifact are what the signer pushed. The status holds the verdict, not the identity that matched.

## Decision

[![The executor reads three things: the Kustomization and its OCIRepository status in the cluster, the declaration in RemediationSettings, and the Git repository through the Git App. The declaration says which repository and path the artifact is built from; the artifact's source and revision annotations are only compared with it. No declaration, a mismatch, an artifact without annotations, an artifact Flux did not verify and an OCIRepository the executor may not read each end NeedsIntervention with their own reason and no Git write. A verified artifact proves only that Flux accepted a signer the writer of the OCIRepository chose. After the merge an OCI unit counts as applied only once the live value matches the desired one; the executor never reads the registry, the artifact's content or any secret.](../assets/diagrams/oci-source-origin.svg)](../assets/diagrams/oci-source-origin.svg "Open full size")

This is option 3 of the issue, with two changes: the declaration has no `branch` field (decision 6 of 2026-11-19), and the artifact must be verified by Flux unless the origin says otherwise.

### 1. The declaration

`RemediationSettings` gets a new list, `spec.ociSources`, next to `spec.repositories`:

```yaml
spec:
  repositories:
  - name: fleet
    url: https://github.com/example/fleet
    targetBranch: main
    provider: GitHub
    github: { ... }
  ociSources:
  - name: apps                  # Name, the list key
    ociRepository:
      namespace: flux-system    # DNS label
      name: apps                # DNS subdomain
    repositoryRef: fleet        # Name of an entry in spec.repositories
    path: clusters/prod         # GitDirPath, default "."
    verification: Required      # Required (default) or NotRequired
```

- `ociRepository` is the Flux object, by namespace and name. A pair appears at most once (a CEL rule, as the URL rule of `repositories`).
- `repositoryRef` must name an entry of `spec.repositories` (a CEL rule on the spec). The mapping checks it again and never relies on admission alone.
- `path` is the directory of the repository that the artifact's root corresponds to, `.` when CI packs the repository root (`flux push artifact --path=./clusters/prod` is `path: clusters/prod`). The build directory of a request is the Kustomization's `spec.path` put under this path, in two steps (section 2, step 7).
- There is no branch field. The branch is the `targetBranch` of the entry `repositoryRef` names, as for a `GitRepository` (ADR-0012 step 2). A second field could only repeat that value or disagree with it. The issue lists the branch among the fields; this is a deliberate departure.
- `verification` is `Required` unless the entry says `NotRequired`. `NotRequired` makes the mapping accept an `OCIRepository` without `spec.verify`. Its risk is in the field's documentation and in limit (a). It is a decision of whoever writes `RemediationSettings`, per origin, and nothing in the artifact or the cluster can turn it on.
- At most 16 entries, as `repositories`. Fields of the `RemediationSettings` status are never read for any decision, as before.

### 2. What the mapping does for a Kustomization whose `sourceRef.kind` is `OCIRepository`

In this order, each stop being `NeedsIntervention` unless said otherwise. A read that fails is returned for retry and is never one of these stops (the rule of `Resolver.get`, `sourcemap.go:315-327`); the one exception is a refused read (step 2).

1. No `ociSources` entry names that namespace and name: stop, reason `OCIOriginNotDeclared`. The message names the object and the field to declare.
2. Read the `OCIRepository` (`get`, by the Kustomization's `spec.sourceRef`, the namespace defaulting to the Kustomization's as for a `GitRepository`, `flux.go:97-99`). Not found: `SourceNotFound`. A 403 or 401 on the read (the grant of section 3 is off): `OCISourceNotReadable`, since a retry could never succeed and would run without end and without a signal.
3. The object must not set `spec.suspend`, `spec.ignore` or `spec.layerSelector`: reason `SourceOptions`, as for the `GitRepository` options at `flux.go:63`. Each can make the artifact differ from the files in Git. `spec.ref` is not constrained: the revision comes from the status.
4. It must be Ready for its current generation (`SourceNotReady`), verified, and applied:
   - **Verified.** `spec.verify` must be set, and the condition `SourceVerified` must be `True` with an `observedGeneration` equal to the object's generation. Otherwise: `OCISourceUnverified`. The executor reads whether `spec.verify` is set and the condition, nothing else of it: no provider, no key, no identity, no registry call. A failed verification is a stop, not a wait: Flux retries it with backoff, and a person re-triggers the request when it verifies. With `verification: NotRequired` this bullet is skipped and the cross-check of step 6 is the only guard (limit (a)).
   - The Kustomization's `status.lastAppliedRevision` must equal `status.artifact.revision` (`RevisionMismatch`; the equality is of two strings from the cluster, as `AppliedFetched` at `fluxstatus.go:227`, with no tag parsing, since the OCI revision is not a Git revision).
5. The artifact must carry `org.opencontainers.image.source` and `org.opencontainers.image.revision` in `status.artifact.metadata`, and the revision must parse as `<ref>@sha1:<40 hex>` or `<ref>@sha256:<64 hex>` (`fluxstatus.ParseRevision`, `fluxstatus.go:184-194`). Otherwise: `OCIOriginUnrecorded`. Only a SHA-1 commit can be checked in step 6 while GitHub is the only ancestry provider; a SHA-256 one ends `OCIOriginUnrecorded` there.
6. The cross-check against the declaration:
   - The annotated source must equal the URL of the declared repository, or equal it with `.git` appended (the form `git config --get remote.origin.url` gives). For a `GitHub` repository the owner and repository names are compared with ASCII case folded, because GitHub treats them as case-insensitive and the settings hold them in lower case (`api/v1alpha1/remediationsettings_types.go:77`); the scheme and host must still match exactly. No other rewriting: not `ssh://`, not `git@host:`.
   - **The ref must be the target branch.** The ref of the annotated revision must equal the repository's `targetBranch` byte for byte. Refused with `OCIOriginMismatch`: a tag (an artifact published from a tag records the tag), another spelling of the branch such as `refs/heads/<branch>`, another branch. There is no list of accepted refs and no field to add one: a declared list would need its own threat note. A pipeline that publishes from tags is refused for now, and the message says that the ref differs, without showing it.
   - The annotated commit must be the head of that branch or one of its ancestors (`AncestryChecker.IsAncestor`, `providers/delivery.go:191`, implemented for GitHub at `internal/providers/github/ancestry.go:39`, a read through the Git App the mapping already opens, `sourcemap.go:222`). The call is made as the operation `read the ancestry of the artifact's commit`. It starts with `read `, so it joins the bounded Git read wait (`gitReadFailure` takes any `sourcemap.RefusedError` and a `sourcemap.TransientError` whose operation starts with `read `, `list ` or `open repository `, `internal/controller/gitread.go:221-227`). The error classes are named, and each has its own test. They are decided before the error reaches the resolver's `transient()` (`sourcemap/errors.go:61-72`), which keeps a refusal as a `RefusedError` and turns every other error into a retry:
     - `ErrInvalidCommit` (the GitHub adapter compares SHA-1 only and refuses a SHA-256 or malformed ID for good, `ancestry.go:40-42`): `OCIOriginUnrecorded`, the commit cannot be compared.
     - `ErrNotFound` (a 404 or 410 of the compare call, `statusError`, `internal/providers/github/client.go:521-536`): `OCIOriginMismatch`, the repository does not have the commit.
     - `ErrForbidden` (403) and `ErrRejected` (422) (`client.go:521-536`): a refusal. It stops the request as a refusal of any other Git read does: the resolver returns a `RefusedError` (`errors.go:61-72`) and the controller reads its class with `refusal` (`internal/controller/pullrequest.go:2212-2226`), with the reasons `GitForbidden` and `GitRejected`. No `OCIOrigin*` reason, no retry.
     - Every other error (a network error, a rate limit, a 5xx): a retry, inside the bounded Git read wait. A failed read is never a verdict.
   - Any difference: stop, reason `OCIOriginMismatch`, no Git write. The message names which comparison differed and shows no URL. The `OCIRepository` is recorded with the other Flux objects the mapping reads (`d.seen`, `sourcemap.go:94-113`) and read again after the Git scan, so an artifact pushed during the scan makes the mapping a retry. It is part of `Result.Observed` too. At the merge the freshness check maps the target again (`freshness.go:327`, `checkSource` at `:655`), which reads the `OCIRepository` as it is then and runs the same cross-check on the current artifact: if it still matches, the plan is fresh; if not, the plan is stale with `SourceChanged` (`freshness.go:680`). An `OCIRepository` that changes during that check makes it a retry (`recheckInputs`, `freshness.go:359`, `:430`, `:488-517`).
7. The build directory is made in two steps, never as one join. First `spec.path` is checked as for a Git source, with `repopath.Join(".", spec.path)` (`sourcemap.go:258`), which refuses a leading `..` and returns the clean path inside the artifact root. Then that result is put under the declared `path`. `repopath.Join(declared, spec.path)` is never called: it resolves `..` inside the declared prefix (`Join("clusters/prod", "../../other")` returns `"other"`), while Flux's kustomize-controller clamps `spec.path` inside the artifact root, so the mapping would scan and patch `other/` outside the declared path. A `spec.path` of `../x` or `../../x` ends `InvalidPath`, as for a Git source.
8. Then the rules of ADR-0012 go on as for a Git source: exactly one settings repository (the declared one), the policy's `repositoryRef`, the `targetBranch`, the build directory, the declaration found by the scan in it, the live value equal to the value in Git, `allowedPaths`. The base commit is the head of the branch, as today.

Reason names are the proposal; the builder may change a spelling in the code review, not the cases.

#### What a verified source proves

An `OCIRepository` is cluster input (invariant 4). It is written by whoever the cluster's RBAC lets create or update the object, and `spec.verify` is whatever that writer put in it. A verified source therefore means one thing: Flux accepted a signature from a signer that the writer of the `OCIRepository` chose. It does not mean the artifact was built from the declared repository, for any provider (cosign with a key, cosign keyless, Notation):

- a key or an identity proves who signed, not which repository the files came from;
- the executor cannot read a signer's identity, only the verdict, and does not try to (see "Tie a keyless signature to the declared repository" under Alternatives).

Verification is kept as the default for defence in depth and nothing more: it stops an artifact that nobody the writer trusts signed from supplying annotations, and a forger needs a signer the writer accepts as well as a registry write. What bounds a forged artifact is the value check against Git, the render check and the review of the pull request.

### 3. What is read, written and granted, and what never is

| | Read | Written | Granted | Never |
| --- | --- | --- | --- | --- |
| Executor, cluster | `get` on `ocirepositories` of the group `source.toolkit.fluxcd.io`: the spec fields above, whether `spec.verify` is set, `status.artifact.revision` and `status.artifact.metadata`, the conditions Ready and `SourceVerified` | nothing new | one new `get` rule in its own ClusterRole, opt-in (below) | `list`, `watch`, any write on the object; Secrets, ServiceAccounts, or the object's `secretRef`, `serviceAccountName`, `provider` and `spec.verify` contents followed; a signature, a key or a certificate read or checked by the executor itself; the artifact's tarball or `status.artifact.url` (an HTTP call to source-controller); the registry, with or without credentials |
| Executor, Git | the head of the declared branch, the ancestry of the annotated commit, files in the declared path, through the GitHub App of the declared repository | the pull request, in a repository of the settings, as today | no new App permission | any repository not in `spec.repositories`; a path or branch taken from an annotation |
| Settings | the declaration is written by whoever may write `RemediationSettings`, a cluster administrator | | | read from the status |
| Analyzer, verifier | | | nothing | `ocirepositories`. The `OCIRepository` read and the comparison with the plan's repository live only on the executor's path (`Verifier.Verify`, not `StatusReader.Status`, `flux.go:125-149`); the analyzer's delivery status tool (`get_delivery_status`) is unchanged |

The grant is opt-in. The chart gets the value `executor.ociSources.enabled`, default `false`, which renders a separate ClusterRole and ClusterRoleBinding with the one rule; kustomize gets the same as a separate component, as the analyzer's module grants (`dist/chart/values.yaml:246-250`, `config/rbac/analyzer/modules/flux/kustomization.yaml:1`). The default install stays as narrow as today. The rules are pinned by the RBAC test tables (`test/rbac/rbac_test.go`, the rows of `gitrepositories` at `:482-499` are the model: executor `get` on `ocirepositories` allowed; executor `list`, `watch` and every write refused; analyzer and verifier refused on every verb) and by the chart tests (`test/chart/chart_test.go`, around `:966`): the ClusterRole and its binding render only with the value on, and the default render has no rule on `ocirepositories` for any identity. With the value off and an entry declared, the mapping ends with `OCISourceNotReadable`, and the lookup page tells the operator to turn it on.

### 4. How the invariants hold

1. **Model output is never authorization.** The declaration is settings written by an administrator, and the annotations are compared, not obeyed. Nothing from the artifact reaches the policy or the model. The plan digest still covers repository, branch, path and build directory (`freshness.go:683`), so a declaration edited between the plan and the merge makes the plan stale (`SourceChanged`). This does not work yet: the call at `freshness.go:661-666` passes only `settings.Spec.Repositories`. The build adds `OCISources` to `sourcemap.Input` and has freshness pass `settings.Spec.OCISources`. Without it every OCI request would go stale at the merge (it fails closed, so it is not a hole, but it is a failure).
2. **Closed catalog.** No new action, parameter or patcher. The action still changes one declared field of one manifest in Git.
3. **Git only.** The only write is the pull request the executor opens today, in a repository of `spec.repositories`, to the entry's `targetBranch`, in a file `allowedPaths` allows. The pipeline that builds the artifact is never touched.
4. **Cluster input is untrusted.** The `OCIRepository` and the two annotations are input from whoever can write them. The annotations are only compared for equality with values the administrator declared, and a difference stops the request. They are never used as a repository, a ref, a path or a URL, never put in a message in full, and never shown to the model. Branch and commit are parsed with the strict parser that also parses Git revisions. Verification is a check on what the writer of the object chose, not on the origin (section 2, "What a verified source proves").
5. **Idempotent.** The mapping adds no state. A restart maps again and gets the same answer or, after a new artifact, a fresh one.
6. **Separate identities.** One new `get` for the executor only, cluster-wide like its `gitrepositories` rule (opt-in, off by default). The analyzer and the verifier get nothing. No registry credential, no Secret read, no new App permission. AGENTS.md invariant 6 is amended in the pull request that builds this, to list the grant and its chart value.

### 5. The merge commit, the delivery check and the verification

Three commits are in play:

- **The base commit** of the pull request is the head of the declared branch when the request is mapped. It is not the artifact's commit. The artifact may be older than the head, so the mapping checks that the artifact's commit is the head or an ancestor of it, and relies on the existing value check (live value equals the value in Git at the head). A change between the artifact's commit and the head that touches the field makes the values differ and stops with `ValueMismatch`; one that does not is harmless.
- **The merge commit** is recorded in the merge receipt as today (`api/v1alpha1/remediationrequest_types.go:554-559`, `:596-604`, ADR-0030 section 1). Nothing about the receipt depends on the source kind.
- **The applied commit** for an OCI unit is the commit in the revision annotation of the artifact the Kustomization applied. The adapter computes it only when `lastAppliedRevision` equals the current `status.artifact.revision` of the `OCIRepository` the Kustomization names, and only when the annotated source names the plan's repository; it fills `AppliedRef` and `AppliedCommit` from the annotation, as it does from `lastAppliedRevision` for a `GitRepository` (`flux.go:236-237`). Then the existing comparison runs unchanged (`delivery.go:146`, `:159-185`, ADR-0030 section 2). Otherwise the status is `Pending`: the executor never reads an older artifact's metadata (it is gone from the status) and never reads the registry.

**What protects the outcome is not the annotation.** An artifact that names the merge commit early would make the delivery look applied before the merged change has arrived. Today that would let `recordApplied` and the move to `Verifying` happen, and the verification would read the old value and end `Inconclusive` with `ValueChanged` at once (`phases.go:555-567`), with a text that says a later commit overwrote the field (`phases.go:688-690`), which is false there. The change that arrives later would never be verified.

**For an OCI unit nothing is recorded as applied until the live value matches.** In `delivered`, after the second answer is `Applied` (`rollout.go:662-670`), an OCI unit counts as applied only when the target the function just read holds the desired value, by the comparison the verification uses (`configured`, `phases.go:670`). It reads nothing new. What differs from today:

- While the value differs, `delivered` returns not applied, as it does for `Pending`. The request stays `WaitingForDelivery` and is requeued at the poll interval inside the window (`phases.go:336-337`, `rollout.go:270-275`), so a value that arrives late is seen. Nothing is recorded: no applied time, no generation, no template hash, no applied commit, and `Verifying` is not entered (`phases.go:320-325`, `:485-488`). This holds with and without `--verify-outcomes`, since both call `delivered`.
- The request shows what any waiting delivery shows: phase `WaitingForDelivery`, `Delivered` `Unknown` with the reason `DeliveryPending`, and `status.deadline` at the end of the window (`enterDelivery`, `phases.go:213-220`). It shows no reason of its own: the wait is the delivery wait.
- When the value matches, the applied time and the other fields are recorded in that write, the request moves to `Verifying`, and the verification reads the field again. A later difference then is a real later change, so `ValueChanged` and its text (`phases.go:688-690`) stay true. Nothing in the verification or its deadline changes, and no second wait exists.
- When the window has passed with the value still different and no read failing, the request ends as a delivery that was not seen: `Inconclusive` with `DeliveryNotObserved` (`phases.go:351-352`; without `--verify-outcomes`, the rollout check ends with `DeliveryNotObserved`, `rollout.go:286-287`, `:500-512`). The built-in message says the Kustomization was not seen applying the commit, which is not what happened here, so for an OCI unit it says that an artifact naming the merge commit was applied and the field never held the desired value within the window. The change is not verified and the ending is final.
- If `configured` cannot read the field (it returns an error, `phases.go:670-680`), that is a failed read: retried, and past the window and its grace `DeliveryNotChecked` (`phases.go:353-361`), never a verdict on the value.
- The window is the existing one: `deliveryWindowEnd` (`rollout.go:321-332`) from the executor's own time of the move to `Merged` (`MergeReceipt.MergedAt`, `internal/controller/limits.go:764-776`), plus the time writes were paused. Both ends of the comparison are the executor's clock, so no two clocks are compared. CI must build and Flux must pull within the hour (limit (d)).
- A Git unit is unchanged.

**The rollout status says where "applied" came from.** The rollout status (`status.rollout`) gets a field `appliedFrom`, an enum recorded in the write that records `appliedRevision` (`phases.go:320-325`; the same for the check without `--verify-outcomes`, `rollout.go:245-252`):

- `GitRevision`: the applied commit is the one in the Kustomization's `lastAppliedRevision`, a `GitRepository` source (today's only case);
- `OCIAnnotation`: the applied commit is the one in the revision annotation of the artifact the Kustomization applied.

It is shown to the reader and read by no decision. Absent on a request recorded before the field existed. ADR-0030 gets a one-line pointer after acceptance, as ADR-0012 does.

**A forbidden read of the `OCIRepository` during the delivery check** (the opt-in grant is off, or was removed) is retried like any failed delivery read today (`phases.go:370-378`) and ends `DeliveryNotChecked` when the window and its grace have passed (`phases.go:353-361`). The one thing this ADR adds is that the cause is shown while it retries. The adapter marks the refused `OCIRepository` read as a lasting cause (`providers.ErrForbidden` at `flux.go:281-282` is shared with the Kustomization read, so the build gives this read its own error, which names the grant), and `lastingCause` gets one case for it (`phases.go:383-397`). `deliveryReadFailed` then writes it into `Delivered` `Unknown` (`phases.go:403-415`), and the final message names it (`phases.go:356-360`). The grant can be turned on meanwhile: each retry reads the object again. No new end path and no early end. Only `Verifier.Verify` makes this read; `StatusReader.Status` is unchanged and gets no grant on the kind.

### 6. Behaviour at the edges

| Case | End state | Reason | Why |
| --- | --- | --- | --- |
| No declaration for the `OCIRepository` | `NeedsIntervention`, no Git write | `OCIOriginNotDeclared` | the repository and path cannot be known from the cluster; the message says what to declare |
| Declared, source, ref or commit not in the branch differs from the declaration | `NeedsIntervention`, no Git write | `OCIOriginMismatch` | the declaration and the artifact disagree about where the files live; a person decides which is right. A tag ref is refused the same way |
| Declared, artifact has no source or revision annotation, or one that does not parse | `NeedsIntervention`, no Git write | `OCIOriginUnrecorded` | see below |
| Declared, the executor may not read `ocirepositories` (at the mapping) | `NeedsIntervention`, no Git write | `OCISourceNotReadable` | permanent until the grant exists |
| The delivery check may not read the `OCIRepository` (403 or 401) | retried; shows the cause on `Delivered`; ends `Inconclusive` when the window and its grace pass | `DeliveryNotChecked` | the existing path for a failed read (`phases.go:353-361`); the grant can be turned on meanwhile |
| `spec.verify` unset, `SourceVerified` not `True` for the current generation (and `verification` is `Required`) | `NeedsIntervention`, no Git write | `OCISourceUnverified` | Flux did not accept the artifact |
| An applied artifact, live value differs, window not passed (OCI unit) | stays `WaitingForDelivery`, requeued | `Delivered` `Unknown`, `DeliveryPending` | the artifact may claim the merge commit early; nothing is recorded as applied |
| An applied artifact, live value differs, window passed (OCI unit) | `Inconclusive` | `DeliveryNotObserved` | final; the change was not seen to arrive |
| Object missing, not Ready, suspended, with `ignore` or `layerSelector`, applied revision differs | as for a `GitRepository` | `SourceNotFound`, `SourceNotReady`, `SourceOptions`, `RevisionMismatch` | the same rules, same reasons, same waits for a reconciling Kustomization |
| Ancestry call (operation `read the ancestry of the artifact's commit`): SHA-256 or malformed commit (`ErrInvalidCommit`), or commit unknown to the host (`ErrNotFound`) | `NeedsIntervention`, no Git write | `OCIOriginUnrecorded`, `OCIOriginMismatch` | permanent answers, never retried |
| Ancestry call: 403 or 422 (`ErrForbidden`, `ErrRejected`) | stops as any refused Git read | `GitForbidden`, `GitRejected` | a refusal is final (`sourcemap/errors.go:61-72`, `pullrequest.go:2212-2226`) |
| Any other read or ancestry call fails (network, rate limit, 5xx) | retried inside the bounded Git read wait, no stop | none | a failed read is never a verdict; the operation starts with `read `, so `gitReadFailure` counts it (`gitread.go:224-227`) |
| Other source kinds (`Bucket`, `ExternalArtifact`, `HelmChart`) | `NeedsIntervention` | `UnsupportedSource` | unchanged |

**An artifact without annotations is refused, not accepted on the declaration alone.** With the declaration alone the executor would have no evidence that the artifact has anything to do with the declared repository, so a wrong declaration (a mistyped path, a repository CI no longer builds from) would open pull requests that deliver nothing. It also could not tell a delivered merge from an undelivered one, since the artifact's revision names no commit: every request would wait the full hour and end `DeliveryNotObserved`. A pipeline records the annotations by adding `--source` and `--revision` to `flux push artifact`, which the CLI requires anyway.

## Consequences

Clusters that deliver through OCI artifacts can get pull requests. The cost is an explicit declaration per `OCIRepository`, an artifact pipeline that records its source from the target branch and is verified by Flux, and one more opt-in grant.

Known limits:

- (a) A verified source proves that Flux accepted a signer the writer of the `OCIRepository` chose, not that the artifact was built from the declared repository (section 2, "What a verified source proves"). Whoever holds the accepted key or identity can sign annotations that match any declaration; with `verification: NotRequired`, anyone who can write to the registry can set them. In both cases the annotations are a cross-check against mistakes and drift, not authentication.
- (b) CI may change the files between Git and the artifact (a substitution step, a generated overlay). The mapping compares only the one field it will change. So is a file CI leaves out with `--ignore-paths` or `--add-ignore-paths`, or that source-controller leaves out: a declaration in such a file is found in Git by the scan and does not exist in what the cluster applies.
- (c) The commit an OCI unit shows as applied comes from an annotation, cluster-side input, where for Git it comes from Flux. The wait of section 5 limits what that can do: nothing is recorded as applied until the live value matches, so an early claim cannot start the verification on the old value. What remains: a live value that matches the desired one for another reason (a person set it by hand) while the merged change is still in transit records the request as applied, and a later overwrite by an older artifact ends it `ValueChanged`; and a change that never arrives costs the whole window and ends `DeliveryNotObserved` instead of an earlier end. A forged annotation can delay or deny that end. It cannot make a wrong value clear.
- (d) The artifact is built after the merge, so the one-hour window includes the CI run and Flux's poll interval. A slower pipeline ends `DeliveryNotObserved` with the change possibly delivered later.
- (e) The delivery is read only while the applied artifact is the current one. Two artifacts in quick succession can leave no moment where the merge commit's artifact is both applied and current. The later one descends from the merge commit and counts. A Kustomization that applied an artifact that is then replaced and never applies another one shows `Pending`.
- (f) The source annotation is compared as a string. A pipeline that records an `ssh://` or `git@` form never matches until it records the HTTPS form. Case is folded for GitHub names only.
- (g) A wrong `path` that still finds one declaration with the right live value opens a pull request in the wrong directory. The render check runs on the build directory the path implies, so it fails when that directory does not build to the same objects; it does not prove the path is the right one.
- (h) `kubectl shadewright doctor` and the analyzer's `get_delivery_status` compare only with a `GitRepository` (`fluxrules/flux.go:190-194`). They keep reporting an OCI source as not compared until a follow-up teaches them, and the analyzer's Flux grant is not widened here.
- (i) The list the mapping copies (`internal/gitops/repopath/generate.go:38-43`) is source-controller's list for a `GitRepository`. Source-controller's OCI exclusions and the `excludeOCI` default of `flux push artifact` are separate lists upstream. The builder compares them with the copied one before it reuses it for an OCI source; a difference is a bug in the build, not a decision.
- (j) A declared `OCIRepository` whose `spec.url` is later pointed at another artifact keeps its declaration. The annotations are still compared on every mapping, so another origin ends `OCIOriginMismatch`, but a pipeline that copies the annotations and is accepted by `spec.verify` passes.

## Alternatives considered

- **Option 1, the declaration alone.** Explicit, and no trust in the artifact. But nothing ties the artifact to the declared repository, and the delivery check could not work: the revision of the artifact is no commit, so every request would end `DeliveryNotObserved` or need a second mechanism to tell a delivered merge. Refused for the reasons of section 6.
- **Option 2, the annotations alone.** The annotations do not say the path, so the path would have to be guessed. They are also set by whoever writes to the registry, so a registry writer would choose where a pull request goes, within the repositories of the settings. That is invariant 4 turned around: input from outside decides a destination. Adding a verification requirement on top is adopted (section 2, step 4) as defence in depth only.
- **Tie a keyless signature to the declared repository (an identity rule).** An earlier draft required, for keyless cosign on GitHub, that `matchOIDCIdentity` be an exact literal naming the declared repository. Rejected, for two reasons. The signing identity of a GitHub workflow names the called workflow (`job_workflow_ref` is "for jobs using a reusable workflow, the ref path to the reusable workflow", GitHub's OIDC reference, read 2026-11-19), so a run in another repository that calls a reusable workflow of the declared one gets the same subject. And `trustedRootSecretRef` lets the writer of the `OCIRepository` supply a trusted root that can mint any subject. The rule would claim a tie it does not provide, and it needs the executor to parse patterns written by someone else.
- **A `GitRepository` kept next to the `OCIRepository`, used only for the mapping.** The mapper could then reuse every Git rule. But the Kustomization does not deliver from that `GitRepository`, so its `lastAppliedRevision` and Ready say nothing about it, and nothing would tie it to the artifact that is applied. The cluster would also fetch a repository only to give the executor a URL, with credentials for it. It trades a declaration in the settings for an object in the cluster that proves less.
- **Declaring a branch, or a list of refs.** See section 1 and section 2, step 6: a branch field can only repeat or contradict `targetBranch`, and a list of refs needs its own threat note.
- **Reading the artifact's content from source-controller.** It would let the mapping read the files that Flux applies. It needs a network path and a grant to source-controller's artifact server, widens the executor's reach much further, and gives content that is again from the cluster side. Not taken.

2. Mapping: `fluxrules` rules for an `OCIRepository` source, the new reasons (among them `OCISourceUnverified`), the declaration, the verification check (step 4) and the ancestry check in `sourcemap`, the strict ref rule, the freshness check with the new input (`sourcemap.Input.OCISources`, passed from `settings.Spec.OCISources`), with the `OCIRepository` recorded in `Observed`, read again after the scan and rechecked by freshness; the reasons added to the metrics list (`internal/controller/metrics.go:155`) and to the explain table (`cmd/kubectl-shadewright/explain.go:255`).
3. Delivery: `AppliedRef` and `AppliedCommit` from the annotation of the current artifact, the plan repository check, `Pending` otherwise; the read of the `OCIRepository` only in `Verifier.Verify`; the lasting cause of a refused read; in `delivered`, an OCI unit applied only while the live value matches, with the OCI message at the end of the window; `appliedFrom` recorded.
4. RBAC: the opt-in ClusterRole in the chart and as a kustomize component, with the RBAC and chart test tables of section 3; AGENTS.md invariant 6, the threat model and the design document updated with the grant.
5. Docs: the reasons page (`docs/reasons.md`), the delivery table of `docs/troubleshooting.md` (its `UnsupportedSource` row says "Use a Git source"), the how-it-works source mapping page, a how-to for declaring an OCI source and for `flux push artifact --source --revision`.
6. Tests that fail without the change: one per reason, the 403 case, the retry cases, a forged annotation that names another repository, and a lab run with an artifact pipeline. Also, each failing without its change:
   - Path: a `spec.path` of `../x` and of `../../x` under a declared path ends `InvalidPath` (it fails against `Join(declared, spec.path)`); a mixed-case annotation of a GitHub repository matches; the `OCIRepository` changing `resourceVersion` mid-scan is a retry.
   - Verification: an `OCIRepository` without `spec.verify`, one with `SourceVerified` `False` (`VerificationError`) and one whose condition has an old `observedGeneration` each end `OCISourceUnverified`; with `verification: NotRequired` the first maps. A key-based and a Notation verification map.
   - Ref: an annotation with a tag, with `refs/heads/<branch>` and with another branch each end `OCIOriginMismatch`.
   - Ancestry, one test per class: `ErrInvalidCommit` gives `OCIOriginUnrecorded`; `ErrNotFound` gives `OCIOriginMismatch`; a 403 and a 422 stop with `GitForbidden` and `GitRejected`; a 5xx, a rate limit and a network error retry, and a failed attempt counts toward the bounded Git read wait.
   - Freshness: an artifact replaced between the plan and the merge by one that matches the declaration leaves the plan fresh; one that does not makes it stale with `SourceChanged`; one replaced while the check runs makes it a retry; an OCI request stays fresh across an unrelated merge and goes stale when the declaration's `path` or `repositoryRef` changes (envtest).
   - Delivery: a 403 on the `OCIRepository` is retried, shows its cause on `Delivered` and ends `DeliveryNotChecked` when the window and grace pass, where a 403 on a `GitRepository` shows no cause as today; the analyzer's delivery status tool reads no `OCIRepository` and the analyzer has no grant on the kind.
   - Early artifact: an OCI unit whose Kustomization reports the merge commit applied while the field holds the old value records nothing and stays `WaitingForDelivery`; it records the applied time and moves to `Verifying` when the value arrives; it ends `DeliveryNotObserved` with the OCI message when the window passes; a Git unit in the same state still records applied at once. `appliedFrom` is `GitRevision` for the Git unit and `OCIAnnotation` for the OCI unit.
   - RBAC: the executor `get` on `ocirepositories` only, with the value on; no rule for any identity with it off; nothing for the analyzer and the verifier either way.
