# ADR-0043: The executor follows its own pull request to any base

- Status: Accepted
- Date: 2026-11-19

## Context

Issue [#892](https://github.com/pkalin/shadewright/issues/892). A person can change the base branch of a pull request on the code host. The executor read its pull request on the target branch only, so a pull request moved to another base looked closed or gone. The request then released the target lock, or opened a second pull request, while the first could still be merged. [ADR-0030](0030-merge-receipt-and-verification-outcomes.md) section 1 says that a restart finds the existing pull request, and [ADR-0021](0021-amending-accepted-adrs.md) says an amendment never widens what is allowed on its own authority. The fix does widen two things, so they are decided here, and the amendments of ADR-0030 and [ADR-0032](0032-azure-devops-as-a-second-git-provider.md) only record them.

The two things:

- A read. `GetChangeRequest` (by number) and `ListChangeRequestsAnyBase` answer a pull request from the request's own `shadewright/` branch on every base branch of the configured repository, where `GetChangeRequest` and `ListChangeRequests` answered only on the target branch.
- One write. `CloseChangeRequestAnyBase` closes the executor's own marked pull request on a base other than the target branch. Its callers are both in the finalizer of a deleted request: `closeOwnOnOtherBases` (every open pull request with the request's marker on another base, with or without a recorded number) and `closeAllOwn` (the recorded number, where the read finds it open on another base). The kill switch gates it like `CloseChangeRequest`.

## Decision

[![A pull request from the request's own branch is read on every base. Open on another base: NeedsIntervention with ChangeRequestOnOtherBase, the lock is kept and nothing but a failed review check is written to it; any open pull request from the branch keeps the lock. Merged on another base: NeedsIntervention with ChangeRequestOnOtherBase, no merge recorded. Closed on another base: handled as closed. From a fork, another repository or another branch: ErrUntrustedAnswer for the whole call of a listing, not the request's by a recorded number. Never on another base: push, comment, merge, a check run other than the failed review check of a stopped request.](../assets/diagrams/other-base-pull-request.svg)](../assets/diagrams/other-base-pull-request.svg "Open full size")

**What is read.** Only pull requests whose head is a `shadewright/` branch of the configured repository and whose base is a branch of that repository. An entry from a fork, from another repository or from another branch is `ErrUntrustedAnswer` for the whole call, never skipped, because the answer is then not to the question asked. A pull request with a number that is not from such a branch is not found. More than `MaxBranchChangeRequests` (100) pull requests from the branch is `ErrTooLarge`: the read fails, the lock stays, and the look is retried. A base name is text from the code host (invariant 4). The provider returns it only when it passes the rule for target branches and leaves it out otherwise; the pull request is still returned with its number, which is what the lock is kept on. A condition message shows the name redacted and cut to 255 bytes.

**What is closed.** Only the executor's own pull request, and only on the deletion of the request: one that carries the request's marker, found by its recorded number or by the listing of every base. The close is retried like the close on the target branch. A recorded number is closed only when that pull request also carries the marker (an unmarked one is read as not the request's and left open), and the finalizer goes after the ones it found, with the exceptions in limit (c). A pull request without the marker is left open. A stop, a cancel, a deadline or a stale plan closes only on the target branch. The one that expires or is cancelled keeps the lock on a pull request open elsewhere and does not close it.

**What is never done on another base.** No push, comment, merge, update of title or body, and no auto-merge, once the executor has seen the pull request there, and no check run except the failed review check `shadewright/review` of a stopped request (amendment of 2026-11-19, limit (e) below). The executor then writes nothing to that pull request except that failed check and the close above. "Its own" pull request means one from the request's branch that carries the request's marker, not one the executor's App authored: a person with write access to the repository who opens a pull request from that branch and copies the marker gets the same treatment, as on the target branch, and every effect of that is a kept lock, a stop or a close.

**Verdicts.** The read by number has two verdicts of its own besides open, merged, closed and gone, and every caller handles them (cancel, deadline, supersede, kill switch, deletion, hint look, settlement; a test walks each stop path with the pull request moved):

- Open on another base: the watch and the adoption stop the request in phase `NeedsIntervention` with reason `ChangeRequestOnOtherBase`, naming the pull request, and the request keeps the lock (`status.holdsTarget`), saying in `TargetHeld` that pull request #N is open on another base and that closing it releases the lock. Moving it back to the target branch does not: the pull request is then open on the target and keeps the lock, and the stopped request only looks at the lock, so it makes no new freshness check there. The step that stops the request fails its review check `shadewright/review` on the head commit, and the later looks of the stopped request write that failed check again while it is not the latest on the head (amendments of 2026-11-19 and 2026-11-20), so the pull request cannot merge on a check written before the stop; besides that check and the close at a deletion, nothing is written to the pull request. A cancel that finds it says so and ends `Cancelled`, with the lock kept while the pull request is open.
- Merged on another base: a merge there delivers nothing the request can verify. The watch and the adoption stop the request in phase `NeedsIntervention` with reason `ChangeRequestOnOtherBase` naming the pull request; it records no merge and keeps no lock. A cancel ends the same way, not `Cancelled`, since the change is merged and may be delivered.
- Closed on another base is handled as closed. A request that lost the write recording its pull request finds it by its marker on any base and in any state, so a restart never opens a second pull request after a person closed, moved or merged the first (invariant 5).

**How the invariants hold.** Invariant 3: the executor opens, pushes and merges nothing on another base, and the one close is of its own marked pull request, the same kind of close it makes on the target branch, on the deletion of the request. It neither bypasses a check nor changes a protected branch. Invariant 5: the marker and the recorded number are what find the pull request again, now on every base, so a restart finds the existing one instead of opening another. Invariant 4: the base name is only compared for equality with the configured target branch (that comparison picks the verdict, the close path and which listed entries are skipped) and shown redacted and bounded; it is never used as a ref, a path or an instruction. A pull request is kept or closed on its number, its head branch, its repository and its marker.

## Consequences

The lock is no longer released because a person moved a pull request. The cost is a second read: with no number recorded, a request lists the pull requests of its branch on every base before it releases, and the finalizer lists them before it goes.

Known limits:

- (a) Removed by the amendment of 2026-11-19: any open pull request from the request's branch keeps the lock on every base, marked or not.
- (b) A merge on another base releases the lock on one read. A base branch that is later merged into the target branch then delivers a change the request did not verify. No request records it. A person is told by the stop reason, `ChangeRequestOnOtherBase`.
- (c) Narrowed by the amendment of 2026-11-19 (a changed target branch no longer stops the close). The finalizer lets go without closing in some cases: when a close or a listing still fails 24 hours after the first failure (`cleanupFailingBound`, and the shorter grace for a refusal), and at once when the plan's repository is gone from the settings (`errRepositoryGone`, also when the `RemediationSettings` object does not exist) or its entry cannot be used (`ErrRepositoryUnusable`), where nothing can be read or closed. A marked pull request can then stay open on another base with no lock, and a person closes it. The Warning Event `PullRequestLeftOpen` says so in each case.
- (d) A cancel, an expiry, a stop or a stale plan closes nothing on another base, so a stopped request can hold the target until a person closes or moves the pull request. `TargetHeld` is the signal.
- (e) A window between a read and a write. The executor reads the pull request and then writes (a handoff's commit to the branch, the review check on the head commit). A person who moves the pull request to another base between the two gets that one write on a pull request that is now elsewhere, and a check run belongs to the commit, so a passing check written before a move also shows on the new base. Branch protection of that base still applies. In the other direction, a pull request moved back to the target branch after the request stopped keeps the review check it had and gets no new one, so a person can merge a plan that is no longer fresh; the request is final and records nothing. Removed by the amendment of 2026-11-19: a stop now fails the review check.
- (f) The cap has no time bound. More than 100 pull requests from the branch keep the lock for as long as they exist: the look fails closed and is retried.

## Alternatives considered

- Ignore other bases. This is the defect of #892: a moved pull request looks gone, the lock is released and a second pull request can be opened.
- Refuse to act and leave the moved pull request open for a person. The lock would be kept, but a deleted request would leave an open pull request carrying its marker and branch, which can still merge.
- Close the marked pull request on another base at a cancel or at expiry. A person moved it there on purpose, and a close on a stop is a second write beyond the target branch that the decision of #892 does not take; the cost is limit (d), and `TargetHeld` tells the person what holds the target.
- Move it back to the target branch. That is a write on a pull request a person changed on purpose, and it can fail on the host's rules.

## Amendments

### 2026-11-19: one verdict table, the lock on any open pull request, a failed check at a stop (#925)

Built in [#925](https://github.com/pkalin/shadewright/issues/925). Limits (a) and (e) in their second half are removed, and limit (c) is narrowed:

- **One verdict table.** Every caller reads what a verdict means from one table in the executor (`verdictTable`), with a row for each verdict and a column for each decision; a test built from the list of verdicts fails when a row or a cell is missing, and another fails when code outside the table compares verdicts. Closed on another base is now a verdict of its own (closed elsewhere), which the callers handle like closed: a close on the target branch has nothing to close there.
- **Gone only after every base.** A recorded number read as not found concludes gone only after the listing of every base found nothing; until then the lock is kept.
- **Limit (a) is removed.** Any open pull request from the request's branch keeps the lock on every base, marked or not, as decided on 2026-11-19. Only a marked one is adopted or closed. `TargetHeld` names the pull request that holds the target.
- **Limit (e), second half, is removed.** A request that stops while its own pull request is open, on the target branch or on another base, fails its review check `shadewright/review` on the head commit: in the step that stops it for a pull request open on another base, and at every look of the stopped holder while the check is not yet failed, so a stop for any other reason gets it at its next look and a failed write is tried again there. While it cannot be written (the Git host fails the write, writes are paused, or the settings permit no write: the repository is gone, its entry cannot be used or names another target branch), the request says so with condition `ReviewCheckNotFailed` and its cause, and a Warning Event `ReviewCheckNotFailed` when the condition is set or its cause changes; the write that records the failed check removes it. A look that finds the request's own pull request no longer open ends the condition, unless another open pull request from the request's branch keeps the lock: that one has the same head, so the condition stays and the look keeps trying the failed check until the lock is released. Moved back to the target branch, the pull request keeps the lock and cannot merge on a check written before the stop. This is the one write besides the close that the executor makes to a pull request on another base: a failed check run, which can only stop a merge. The section "What is never done on another base" holds with that exception. The first half of limit (e), the window between a read and a write, stays.
- **Limit (c) is narrowed.** The finalizer of a request whose repository entry now names another target branch closes its own pull requests through the recorded target branch and on every other base, instead of letting go. When the plan's repository is gone from the settings, its entry cannot be used, or the `RemediationSettings` object does not exist, nothing can be read or closed: the finalizer still goes, and records the Warning Event `PullRequestLeftOpen` in that case too, naming which of these it is.
- **The provider contract.** A listing never leaves out the name of the target branch; an empty base name always means another base.
- **The failed check stays the last one (2026-11-20).** A reconcile that worked from an older cached copy of the request could write a pending check over the failed one a stop had just written, and the request stayed stopped with a check that no longer said so (the Git waits model, one seed in 200,000). This is the executor overwriting its own verdict, not the window of limit (e), so it is fixed: before the merge gate writes the review check (in progress, passed, or failed on too many reviews) the request is read live, from the API server, and a request that is stopped, released or being deleted there gets no check from that reconcile; a failed live read writes nothing, sets condition `Approved` False with reason `ReviewCheckLiveReadFailed` until a look writes the check or needs no write, and the look is tried again at its usual pace. The failed check of a stale plan, a cancel or a stop is written without that read: nothing it can go over passes a merge. A stopped request whose own pull request is open also reads the latest review check of the head at each of its looks once the failed check is recorded, and writes the failed check again when the Git host shows another state last or none: one read and at most one write per look, within the looks above, with no polling of its own. A look that cannot tell (the read fails, or the settings permit no read) writes nothing and records the Warning Event `StoppedCheckUnread` once when such looks start on a head. Both are reads and writes this amendment already allows (the request itself, and the check run `shadewright/review` on the head of its own pull request); nothing is widened.
- Still a known limit: a pull request reopened after the request released the lock does not take the lock back. A released request asks the Git host nothing, and taking the lock again needs an admission path of its own; that is split out to [#940](https://github.com/pkalin/shadewright/issues/940).
